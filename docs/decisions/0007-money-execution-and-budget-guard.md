# 0007. 돈 실행 지점 하나와 예산 가드

- 상태: 제안 (이 PR에서 리뷰)
- 날짜: 2026-11-04
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0002](0002-budget-guard-and-scope.md) 예산 관리, [ADR 0004](0004-agent-integration.md) 승인은 서버가 강제, [budget.md](../planning/budget.md) 결제 검사

## 결정

1. **돈이 나가는 모든 일은 service의 실행 함수 하나를 지난다.** 이체, 체크·신용카드 결제, 대출 상환, 목표 저축 이체, 승인된 `pending_actions` 실행이 모두 같은 함수(가칭 `MoneyMovementService.execute`)로 간다.
2. 그 함수 안, **잔액을 바꾸기 바로 앞에 가드 목록**을 둔다. 첫 가드가 **예산 가드**다. 예산 관리를 신청한 사용자에게만 동작한다.
3. 예산 가드는 **LLM이 아니라 코드**다. 웹·우리 Agent·MCP·카드 결제 어느 입구로 들어와도 같은 검사를 받는다.
4. **"항상 통과" 업종은 사용자가 고른다.** 의료·약국은 처음 신청할 때 추천값으로 켜 두고, 사용자가 끄거나 다른 분류(육아, 반려동물 병원 등)를 추가할 수 있다.
5. **가드를 약하게 만드는 설정 변경은 PIN 승인이 필요하다.** 항상 통과 업종 추가, 필수 → 선택 변경 등은 `pending_actions`를 거친다. 가드를 강하게 하는 변경(항상 통과 해제 등)은 바로 실행한다.

```
웹 이체 ─────────┐
Agent 이체 요청 ──┤               ┌─ 승인 필요 ─▶ pending_actions ─▶ (PIN 승인) ─┐
MCP 이체 요청 ───┼─▶ 요청 검증 ───┤                                              │
카드 결제 ───────┤               └─ 바로 실행 ──────────────────────────────────┤
대출 상환·저축 이체 ┘                                                              ▼
                          ┌──────────────── 돈 실행 지점 (함수 하나, 트랜잭션 하나) ────────────────┐
                          │ ① 예산 주기 행 잠금 (budget_cycles, 예산 신청자만)                     │
                          │ ② 계좌 행 잠금 (계좌 id 오름차순)                                     │
                          │ ③ 가드: 예산 가드 → (나중에 다른 가드)                                 │
                          │ ④ 잔액·한도 검사                                                     │
                          │ ⑤ 장부 기록 + 잔액 변경 + pending_actions 상태 변경                    │
                          └───────────────────────────────────────────────────────────────────────┘
```

## 배경

- budget.md는 "예산을 넘는 결제는 사용자가 확인해야 실행"을 정했지만, **어디서 검사하는지**는 정하지 않았다.
- 돈이 나가는 길이 여러 개다(웹 이체, Agent, MCP, 카드 결제, 대출 상환, 목표 저축 이체). 각자 잔액을 빼면 검사를 여러 곳에 붙여야 하고 하나는 빠진다.
- MCP로 들어온 요청은 우리 LangGraph를 지나지 않는다. 예산 검사가 Agent에 있으면 그 입구는 지킬 수 없다(ADR 0006).
- 승인 대기(`pending_actions`)는 요청하고 몇 분 뒤에 실행된다. 그사이 카드를 또 쓰면 상황이 바뀐다.
- 필수 업종은 사람마다 다르다. 의료비가 거의 없는 사람도 있고, 반려동물 병원비나 육아용품처럼 미룰 수 없는 지출이 따로 있는 사람도 있다.

## 예산 가드의 판단

| 상황 | 결과 |
|---|---|
| 예산 관리를 신청하지 않은 사용자 | 통과 |
| 지출이 아닌 이동: 내 계좌끼리, 목표 저축 이체, 신용카드 대금 출금 | 통과 (budget.md "돈의 종류") |
| 사용자가 **항상 통과**로 고른 업종 | 통과 + 기록. **자유 사용 가능액에서는 그대로 차감** |
| 금액 ≤ 자유 사용 가능액 | 통과 |
| 금액 > 자유 사용 가능액 | **멈춤**: `409 BUDGET_CONFIRMATION_REQUIRED` + 예산 확인용 `pending_actions` |
| 사람이 PIN으로 확인한 예산 초과 건 (`action_id`가 있는 실행) | 다시 계산해서 확인 때보다 나빠지지 않았으면 통과, `budget_decisions`에 기록. 나빠졌으면 같은 승인 대기를 갱신해서 다시 확인 요청 |

마지막 줄이 없으면 승인한 건이 다시 가드에 걸려 확인 요청을 반복한다.

## 예산 설정 변경과 승인

| 변경 | 가드에 미치는 영향 | 처리 |
|---|---|---|
| 항상 통과 업종 **추가** | 약해짐 | `pending_actions` + PIN |
| 필수 업종 → 선택, 선택 → 필수 | 계산이 바뀜 (예산 Agent가 제안 가능) | `pending_actions` + PIN |
| 항상 통과 업종 **해제** | 강해짐 | 바로 실행 |
| 월 수입·고정 지출·예상 생활비 변경 | 계산이 바뀜 | budget.md 규칙 10: 사용자 승인 후. 이 ADR에서 **PIN 승인**으로 정한다 |

Agent는 사용자 토큰을 가지고 있다. 설정 변경이 바로 실행되면 Agent나 MCP가 "쇼핑도 항상 통과"로 바꾼 뒤 결제해서 가드를 우회할 수 있다. 카드 정지는 바로, 해제는 승인으로 한 것과 같은 원칙이다(**안전해지는 쪽은 바로, 위험해지는 쪽은 승인**).

## 검토한 대안

### 예산 검사 위치

| 대안 | 결과 |
|---|---|
| 예산 Agent(LLM)가 결제 전에 검사 | MCP 입구를 지킬 수 없음. LLM이 빼먹거나 계산을 틀릴 수 있음. 버림 |
| HTTP 미들웨어 | 요청마다 모양이 달라 "얼마짜리 지출인지" 모름. DB 잠금과 같은 트랜잭션에 들어갈 수 없음. 버림 |
| `pending_actions`를 만들 때 검사 | 승인은 몇 분 뒤. 그사이 상황이 바뀜. 버림 (안내용으로는 요청 때도 미리 계산해서 보여 줌) |
| 이체·카드·대출 service마다 검사 | 세 군데에 같은 코드. 하나가 빠지면 구멍. 버림 |
| **실행 함수 하나 + 가드 목록** | **채택**. 어느 입구든 반드시 지나가고, 잠금 안에서 검사해서 동시 결제에도 정확함 |

### 필수 업종

| 대안 | 결과 |
|---|---|
| 의료·약국을 시스템이 고정 (기존 budget.md) | 사람마다 다른 지출을 반영하지 못함. 버림 |
| **사용자가 업종별로 선택, 의료·약국은 추천값** | **채택** |
| 항상 통과 업종에 주기당 상한 (예: 의료 30만 원까지) | 과함. 범위 밖으로 기록만 해 둠 |

## 결과

**좋아지는 점**
- 예산 보호가 **입구와 상관없이** 하나의 코드에서 이뤄진다. "MCP로 이체 요청 → 예산 초과면 멈춤"을 테스트로 증명할 수 있다.
- ERD 규칙 4(돈 이동은 한 트랜잭션)와 규칙 5(잠금 순서)를 **한 함수가** 지킨다.
- 나중에 다른 가드(해외 결제 차단, 이상 거래 감지 등)를 같은 자리에 끼울 수 있다.

**감수할 점**
- 이체·카드·대출 기능을 만들 때 각자 잔액을 바꾸지 않고 **반드시 실행 함수를 거쳐야** 한다. 리뷰에서 지켜야 하고, "잔액을 직접 바꾸는 코드는 실행 함수 안에만"을 테스트나 규칙으로 확인한다.
- 예산 신청자는 결제마다 주기 행을 잠가서, 같은 사용자의 결제는 하나씩 처리된다(의도한 것).
- 예산 설정 변경에도 PIN이 필요해서 조금 번거롭다.

**팀 뼈대와의 차이**
- 팀 뼈대는 `transfers`·`cards` service가 각자 잔액을 바꾼다. 이 레포는 돈 실행 지점을 하나로 모은다.
