# 0007. 돈 실행 지점 하나와 예산 가드

- 상태: 채택 (실행 함수 구현: `domains/accounts/money.py`, 이체부터 적용. 예산 가드는 예산 기능 PR에서)
- 날짜: 2026-11-04
- 관련 PR: #5
- 관련: [ADR 0002](0002-budget-guard-and-scope.md) 예산 관리, [ADR 0004](0004-agent-integration.md) 승인은 서버가 강제, [budget.md](../planning/budget.md) 결제 검사

## 결정

1. **잔액이나 장부를 바꾸는 모든 일은 service의 실행 함수 하나를 지난다**(가칭 `MoneyMovementService.execute`). 출금(이체, 체크카드 결제, 대출 상환, 목표 저축 이체), 입금(월급, 이자, 환불, 대출금), 신용카드 사용 기록(`card_transactions`)이 모두 여기를 지난다.
2. 그 함수 안, 기록하기 바로 앞에 **가드 목록**을 둔다. 첫 가드가 **예산 가드**다. 예산 관리를 신청한 사용자의 **지출**에만 동작하고, 입금에는 동작하지 않는다.
3. 예산 가드는 **LLM이 아니라 코드**다. 웹·우리 Agent·MCP·카드 결제 어느 입구로 들어와도 같은 검사를 받는다.
4. **"항상 통과" 업종은 사용자가 고르되, 카드 결제에만 적용한다.** 업종은 요청한 쪽이 아니라 **서버가 가맹점 정보로 정한 값**을 쓴다. 이체는 항상 검사한다(요청에 "의료"라고 적어서 통과하는 것을 막음).
5. **예산 가드를 약하게 만드는 변경은 모두 PIN 승인이 필요하다.** 목록은 이 문서의 ["가드를 약하게 하는 변경"](#가드를-약하게-하는-변경) 표 하나만 기준으로 삼고, 다른 문서는 이 표를 링크한다. 승인 강제는 **REST API에서** 한다. 해당 API는 바로 실행하지 않고 `pending_actions`만 만든다. 그래서 MCP 도구로 불러도 사람이 PIN을 넣어야 반영된다.
6. **예산을 넘는 이체는 PIN 한 번**으로 이체와 예산 확인을 같이 받는다. 승인 때 본 숫자보다 실행 때 상황이 나빠졌으면 **실패로 끝내고** 사용자가 다시 요청한다(자동으로 다시 확인을 만들지 않음).

```
웹 이체 ─────────┐
Agent 이체 요청 ──┤               ┌─ 승인 필요 ─▶ pending_actions ─▶ (PIN 승인) ─┐
MCP 이체 요청 ───┼─▶ 요청 검증 ───┤   (예산 미리 계산 결과를 같이 저장)            │
카드 결제 ───────┤               └─ 바로 실행 ──────────────────────────────────┤
월급·이자·대출금 ──┘                                                              ▼
                          ┌──────────────── 실행 함수 (함수 하나, 트랜잭션 하나) ────────────────┐
                          │ ① 예산 주기 행 잠금 (budget_cycles, 예산 신청자의 지출만)               │
                          │ ② 계좌 행 잠금 (계좌 id 오름차순)                                     │
                          │ ③ 가드: 예산 가드 (지출만) → (나중에 다른 가드)                         │
                          │ ④ 잔액·한도 검사                                                     │
                          │ ⑤ 장부(또는 card_transactions) 기록 + 잔액 변경 + 승인 대기 상태 변경    │
                          └───────────────────────────────────────────────────────────────────────┘
```

- **돈이 움직이지 않는 승인 작업**(카드 정지 해제, 예산 설정 변경)은 실행 함수를 지나지 않는다. 승인 처리기가 PIN 확인 후 같은 트랜잭션에서 해당 도메인 service를 부른다.
- 신용카드 결제는 계좌 잔액을 바꾸지 않지만, 쓴 순간 예산에서 차감되므로(ADR 0002) 같은 함수에서 예산 가드를 거친 뒤 `card_transactions`에 기록한다.

## 배경

- budget.md는 "예산을 넘는 결제는 사용자가 확인해야 실행"을 정했지만, **어디서 검사하는지**는 정하지 않았다.
- 돈이 나가는 길이 여러 개다(웹 이체, Agent, MCP, 카드 결제, 대출 상환, 목표 저축 이체). 각자 잔액을 바꾸면 검사를 여러 곳에 붙여야 하고 하나는 빠진다.
- MCP로 들어온 요청은 우리 LangGraph를 지나지 않는다. 예산 검사가 Agent에 있으면 그 입구는 지킬 수 없다(ADR 0006).
- Agent는 사용자 토큰을 가진다. 토큰으로 할 수 있는 **정상 동작을 이어 붙여 가드를 끄는 길**(설정을 바꾼 뒤 결제, 이체에 업종을 적기)도 막아야 한다.
- 예산을 넘어도 막으면 안 되는 업종은 사람마다 다르다. 의료비가 거의 없는 사람도 있고, 반려동물 병원비나 육아용품처럼 미룰 수 없는 지출이 따로 있는 사람도 있다.

## 용어

| 용어 | 뜻 | 저장 위치 |
|---|---|---|
| **항상 통과 업종** | 예산을 넘어도 막지 않는 **카드 결제 업종** (추천값: 의료·약국) | `budget_profiles.category_settings` |
| **필수 생활비 분류** | 남은 일수만큼 **미리 떼어 두는** 매일 쓰는 지출 (식사·교통) | `budget_profiles.category_settings` |

두 설정은 따로다. 의료는 보통 "항상 통과"지만 "필수 생활비"는 아니다(매일 쓰지 않음).

## 예산 가드의 판단

| 상황 | 결과 |
|---|---|
| 예산 관리를 신청하지 않은 사용자, 또는 입금 | 통과 (검사 안 함) |
| 지출이 아닌 이동: 내 계좌끼리, 목표 저축 이체, 신용카드 대금 출금 | 통과 (budget.md "돈의 종류") |
| **카드 결제**이고, 서버가 정한 가맹점 업종이 사용자의 항상 통과 업종 | 통과 + 기록. 자유 사용 가능액에서는 **그대로 차감** |
| 금액 ≤ 자유 사용 가능액 | 통과 |
| 금액 > 자유 사용 가능액, **승인 없이 실행되는 카드 결제** | **멈춤**: `409 BUDGET_CONFIRMATION_REQUIRED` + 예산 확인용 `pending_actions` |
| 금액 > 자유 사용 가능액, **승인을 거쳐 실행되는 이체·대출 상환** | 아래 "예산을 넘는 승인 건" 규칙 |

### 예산을 넘는 승인 건

이체처럼 원래 PIN 승인이 필요한 일은 **요청 때 예산을 미리 계산**해서, 넘으면 같은 승인 화면에서 함께 확인받는다. PIN은 한 번이다.

1. **요청 때**: 서버가 자유 사용 가능액을 계산해서 `pending_actions.payload`의 `budget_check`에 저장한다: `{"free_before": 120000, "amount": 300000, "over": true}`. 넘으면 승인 화면에 영향 설명("월세 낼 돈이 부족해져요")과 사유 입력칸이 함께 나온다.
2. **승인 때**: 사용자가 사유를 적고 PIN을 넣는다. 사유는 `budget_decisions`에 남는다.
3. **실행 때**(같은 트랜잭션, 잠금 안): 자유 사용 가능액을 다시 계산한다.
   - 지금 값 ≥ `free_before` (승인 때 본 것보다 나빠지지 않음) 또는 금액 ≤ 지금 값 → **통과**
   - 그 외(그사이 다른 결제로 더 나빠짐) → `FAILED`, `failure_reason = BUDGET_CHANGED`. 돈은 움직이지 않는다. 사용자는 바뀐 숫자를 보고 **새 요청**을 한다(새 멱등키).
4. 실패를 자동으로 새 확인 요청으로 바꾸지 않는다. 그래서 확인이 끝없이 반복되지 않고, 실패 처리도 롤백 없이 상태 하나만 바꾸면 된다.

카드 결제는 원래 승인이 없어서, 넘을 때만 예산 확인용 `pending_actions`(`action_type = BUDGET_CONFIRM`)를 만들고 같은 규칙 1~4를 따른다.

## 가드를 약하게 하는 변경

**판단 기준: 자유 사용 가능액을 늘리거나, 지출을 검사에서 빼는 변경이면 PIN이 필요하다.** 반대 방향은 바로 반영한다.

| PIN 필요 (`pending_actions`) | 바로 반영 |
|---|---|
| 항상 통과 업종 **추가** | 항상 통과 업종 **해제** |
| 필수 생활비 분류 **해제**, 예상 생활비 **낮추기** | 필수 생활비 분류 **추가**, 예상 생활비 **높이기** |
| 고정 지출 **삭제·금액 낮추기** | 고정 지출 **추가·금액 높이기** |
| 목표 **삭제·금액 낮추기**, 이번 주기 목표 저축 **묶음 풀기** | 목표 **추가·금액 높이기** |
| 월 수입 **높이기** | 월 수입 **낮추기** |
| 예산 관리 **해지** | 예산 관리 **신청** |

- 이 표가 PIN 대상의 **유일한 기준**이다. ERD 승인 표, budget.md, user-flows.md는 이 표를 링크한다.
- 실제 월급이 예상과 달라서 수입이 바뀌는 것은 시스템이 하는 일이라 승인이 없다(budget.md 규칙 1).
- 예산 Agent는 변경을 **제안**만 하고(`propose_budget_change`), 제안은 위 표에 따라 바로 반영되거나 승인 대기가 된다.

## 검토한 대안

### 예산 검사 위치

| 대안 | 결과 |
|---|---|
| 예산 Agent(LLM)가 결제 전에 검사 | MCP 입구를 지킬 수 없음. LLM이 빼먹거나 계산을 틀릴 수 있음. 버림 |
| HTTP 미들웨어 | 요청마다 모양이 달라 "얼마짜리 지출인지" 모름. DB 잠금과 같은 트랜잭션에 들어갈 수 없음. 버림 |
| `pending_actions`를 만들 때만 검사 | 승인은 몇 분 뒤. 그사이 상황이 바뀜. 버림 (요청 때는 **미리 계산해서 보여 주는 용도**로만 씀) |
| 이체·카드·대출 service마다 검사 | 같은 코드가 여러 곳. 하나가 빠지면 구멍. 버림 |
| **실행 함수 하나 + 가드 목록** | **채택**. 어느 입구든 반드시 지나가고, 잠금 안에서 검사해서 동시 결제에도 정확함 |

### 실행 때 상황이 나빠졌을 때

| 대안 | 결과 |
|---|---|
| 같은 승인 대기를 갱신해서 다시 확인 요청 | 승인·실행이 한 트랜잭션이라 실패 롤백 때 갱신도 사라짐. 확인이 반복될 수 있음. 버림 |
| **실패로 끝내고 사용자가 새로 요청** | **채택**. 단순하고, 사용자가 바뀐 숫자를 보고 다시 판단함 |

### 항상 통과 업종

| 대안 | 결과 |
|---|---|
| 의료·약국을 시스템이 고정 (기존 budget.md) | 사람마다 다른 지출을 반영하지 못함. 버림 |
| 사용자가 선택, 이체에도 적용 | 이체에는 서버가 아는 업종이 없어서 요청에 적은 값을 믿어야 함. 우회 가능. 버림 |
| **사용자가 선택, 카드 결제에만, 업종은 서버가 정함** | **채택** |
| 항상 통과 업종에 주기당 상한 (예: 의료 30만 원까지) | 과함. 범위 밖으로 기록만 해 둠 |

## 결과

**좋아지는 점**
- 예산 보호가 **입구와 상관없이** 하나의 코드에서 이뤄진다. "MCP로 예산 초과 이체 요청 → PIN 없이는 실행 안 됨", "설정을 바꿔도 PIN 없이는 반영 안 됨"을 테스트로 증명할 수 있다.
- ERD 규칙 4(돈 이동은 한 트랜잭션)와 규칙 5(잠금 순서)를 **한 함수가** 지킨다.
- 나중에 다른 가드(해외 결제 차단, 이상 거래 감지 등)를 같은 자리에 끼울 수 있다.

**감수할 점**
- 이체·카드·대출 기능을 만들 때 각자 잔액을 바꾸지 않고 **반드시 실행 함수를 거쳐야** 한다. "잔액·장부를 바꾸는 코드는 실행 함수 안에만"을 리뷰와 테스트로 확인한다.
- 예산 신청자는 지출마다 주기 행을 잠가서, 같은 사용자의 지출은 하나씩 처리된다(의도한 것).
- 승인 때와 실행 때 사이에 다른 결제가 있으면 이체가 실패할 수 있다. 사용자는 다시 요청해야 한다.
- 예산 설정을 느슨하게 바꿀 때마다 PIN이 필요해서 조금 번거롭다.

**팀 뼈대와의 차이**
- 팀 뼈대는 `transfers`·`cards` service가 각자 잔액을 바꾼다. 이 레포는 실행 지점을 하나로 모은다.
