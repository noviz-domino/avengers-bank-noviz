# 0016. Agent 실행 추적과 응답 시간: Langfuse 클라우드, 감독관은 턴마다 한 번 계획, 생각 수준 low

- 상태: 채택
- 날짜: 2026-11-06
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0006](0006-agent-orchestration.md) "다시 검토할 조건", [ADR 0015](0015-agent-chat.md) Agent 구현

## 결정

1. **실행 추적은 Langfuse 무료 클라우드**(사용자 결정). `.env`에 프로젝트 키(`LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`)가 있으면 채팅마다 감독관·담당·도구·Gemini 호출이 단계별로 남는다. 사용자는 `user-{id}`, 대화방은 `session_id`로 묶인다. 키가 없으면 꺼지고, 테스트는 항상 끈다.
2. **감독관은 턴 처음에 한 번만**, 처리할 담당을 **순서대로 담은 계획**(`Plan.agents`)을 낸다. 담당이 끝날 때마다 감독관을 다시 부르지 않는다. 같은 담당은 한 번만, 최대 3개.
3. **Gemini 생각 수준 기본값 `low`**(`GEMINI_THINKING`). Agent(감독관·담당)와 RAG 답변에 같이 적용한다. `minimal`은 gemini-3.8-flash가 지원하지 않는다(400).
4. **측정 명령**: `python -m avengers_bank.domains.agent.evaluate`. 읽기만 하는 질문 14개(`agent/routing.jsonl`)로 라우팅 정확도, 질문당 LLM 호출 수, 응답 시간 p50·p95를 잰다. 이체·분실 신고처럼 데이터를 바꾸는 질문은 반복 측정하지 않는다.

## 측정 (2026-11-06, gemini-3.8-flash, 데모 계정, 질문 14개)

| 설정 | 라우팅 | 질문당 LLM 호출 | p50 | p95 |
|---|---|---|---|---|
| 개선 전: 담당마다 감독관 다시 호출, 생각 기본값 | 14/14 | 4.1 | 15.0초 | 28.5초 |
| 계획 감독관, 생각 기본값 | 14/14 | 3.2 | 12.6초 | 19.7초 |
| 계획 감독관, 생각 `low` (Agent만) | 14/14 | 3.2 | 8.4초 | 18.8초 |
| **계획 감독관, 생각 `low` (Agent + RAG)** | 13/14 | 3.1 | **8.2초** | **16.8초** |
| 생각 `minimal` | — | — | — | 모두 400 (지원 안 함) |

- 마지막 측정에서 "스타크 신용카드 혜택"이 카드 담당으로 갔다. 감독관 규칙에 "카드 **상품**의 혜택·연회비는 product"를 더했고, **그 질문 하나만** 다시 물었을 때 상품 담당으로 갔다(14개 전체 재측정은 하지 않음).
- LLM 호출 한 번이 3~4초라서, 호출 수를 줄이는 것이 시간을 줄이는 가장 직접적인 방법이었다.
- p95를 끌어올리는 것은 복합 요청(LLM 6번)과 약관 질문(Agent 안에서 RAG가 Gemini를 한 번 더 부름)이다.

## 배경

- 실제 Gemini 점검(ADR 0015)에서 한 턴이 12~45초였다. ADR 0006의 "다시 검토할 조건"(p95 8초)을 크게 넘었다.
- 감독관이 담당이 끝날 때마다 다시 고르는 구조는 "끝났다(FINISH)"를 확인하는 호출이 매 턴 하나 더 들었다.

## 검토한 대안

| 주제 | 대안 | 결과 |
|---|---|---|
| 추적 | Docker로 Langfuse 직접 | v3는 PostgreSQL·ClickHouse·Redis·MinIO까지 컨테이너 5~6개. 버림 (사용자 결정) |
| 추적 | 로그만 | 노드별 시간·입출력을 보기 어려움. 버림 |
| 호출 줄이기 | 감독관 없이 Agent 하나 + 도구 16개 | 도구를 헷갈림(ADR 0006). 버림 |
| 호출 줄이기 | **감독관이 턴 처음에 계획** | **채택**. 측정에서 단일 요청 4~5번 → 3~4번, 복합 8번 → 6번 |
| 호출 줄이기 | 복합 요청의 담당을 동시에 | 순서가 필요한 요청("정지하고 잔액")이 있고 줄어드는 것은 p95 일부. 다음에 |
| 생각 수준 | `minimal` | 모델이 지원 안 함 |

## 결과

**좋아지는 점**
- p50 15.0초 → 8.2초, p95 28.5초 → 16.8초. 라우팅은 그대로 거의 다 맞음.
- 감독관이 턴 처음(사람 말 직후)에만 불려서 "AI로 끝나는 요청" 문제가 감독관에서는 생기지 않는다.
- 느린 턴을 Langfuse에서 노드별로 열어 볼 수 있다.

**감수할 점**
- 여전히 ADR 0006의 기준(p95 8초)을 넘는다. 다음 후보: 복합 요청의 담당 동시 실행, 약관 질문을 상품 Agent 없이 RAG로 바로(LLM 1번 절약), 응답 스트리밍(체감 시간).
- 계획 방식은 앞 담당의 결과를 보고 다음 담당을 바꾸지 못한다. 예: "카드 정지하고 잔액"에서 정지가 실패해도 잔액은 알려준다. 은행 상담의 복합 요청은 대부분 서로 독립이라 감수한다.
- 생각 수준을 낮춰 판단이 조금 거칠어질 수 있다(측정에서 14개 중 1개 오분류, 규칙 보강으로 고침). 질문이 늘면 다시 잰다.
- `low`는 RAG 답변에도 적용된다. 검색 지표(ADR 0013)는 그대로지만, **근거 기반 답변의 품질(정확성·인용)은 따로 재지 않았다**. 답변 채점 세트를 만들 때 함께 잰다.
- 사용자가 채팅에 PIN 같은 민감 정보를 직접 쓰면 그대로 Langfuse로 나간다. 실서비스라면 SDK의 가리기(mask) 기능이나 직접 호스팅이 필요하다.
- Langfuse 클라우드로 대화 내용·도구 결과(데모 데이터의 잔액·계좌번호)가 나간다. 실제 고객 데이터라면 직접 띄우거나 가린 뒤 보내야 한다.
- 측정은 한 번씩이라 질문 14개의 p95는 사실상 가장 느린 1~2개다. 결론은 경향으로 본다.
