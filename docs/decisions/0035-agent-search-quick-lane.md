# 0035. 검색형 빠른 길: 라우터가 기간·업종을 채우고 서버 합계로 답한다

- 상태: 채택
- 날짜: 2026-11-27
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0034](0034-agent-quick-lanes.md) 빠른 길, [조사 보고서](../research/agent-latency-and-rag.md) 1순위 제안, [평가 기록](../evaluations/agent-latency/README.md)

## 배경

- 빠른 길(ADR 0034) 뒤에도 p95를 끌어올린 것은 "이번 달 식비 얼마 썼어?", "이번 달에 편의점에서 얼마 썼어?" 같은 검색형 질문이었다. 담당 Agent가 기간·업종을 고르고 한 번에 못 찾으면 다시 찾아서 LLM을 3~5번 불렀다.
- 거래 검색 API(`GET /transactions`)는 조건 전체의 들어온 돈·나간 돈 합계(`total_in`·`total_out`)를 서버가 계산해 돌려준다. 그래서 조건만 정해지면 모델이 계산할 일이 없다.
- 조사 보고서는 "미리 불러오기"보다 이 검색형 빠른 길을 1순위로 권했다. 최근 몇 건을 미리 넣는 방식은 기간 합계 질문에 답하지 못하고 틀린 합계를 만들 위험이 크기 때문이다.

## 결정

1. **라우터가 검색 조건을 채운다** (`Plan.from_date`·`to_date`·`categories`·`keyword`·`direction`, `quick`에 `search`). 라우터 프롬프트 끝에 오늘 날짜를 붙여 "이번 달", "지난주"를 날짜로 바꾸게 한다(날마다 바뀌는 부분을 끝에 두어 앞부분은 늘 같게).
2. **업종 목록에 있으면 `categories`, 없으면 `keyword`**: "식비"는 식사와 외식·술자리 두 업종, "편의점"은 업종 목록에 없어서 낱말(거래 메모·상대방 이름에서 찾음). 업종은 최대 3개.
3. **코드가 업종마다 한 번씩 검색하고 서버 합계만 더한다** (`agent/quick.py`의 `spending`). 답은 "기간 + 대상 + 쓴 돈/들어온 돈 합계"와 최근 5건이다. 5건보다 많으면 "최근 5건만 보여요. 합계는 기간 전체예요."를 붙인다. 거래 날짜는 한국 날짜로 보여 준다.
4. **조건이 이상하면 코드가 답하지 않는다**: 기간이 없거나 날짜 형식이 틀리거나 시작이 끝보다 늦거나 끝이 오늘보다 뒤면 담당 Agent가 처리한다. 라우터의 날짜 실수가 틀린 답이 되지 않게.
5. **카드 사용내역은 아직 넣지 않는다**: MCP 카드 사용내역 도구는 카드 하나(`card_id`)를 받아서 "어느 카드인지"를 먼저 골라야 한다. 다음 후보로 남긴다.

## 검토한 대안

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 최근 거래 몇 건을 담당 Agent에 미리 넣기 | 도구 고르기 호출 하나를 줄임 | 기간 합계는 미리 넣은 창 밖에 있어서 결국 검색 도구를 부르거나 틀린 합계를 말함 (조사 보고서) |
| 모델이 거래 목록을 받아 직접 더하기 | 서버 변경 없음 | 숫자 계산은 모델이 틀리기 쉬움. 서버가 이미 합계를 준다 |
| 업종 하나만 받기 | 단순 | "식비"처럼 업종이 둘 이상인 말이 흔함. 서버 합계를 업종마다 받아 코드가 더하면 계산이 정확함 |

## 결과

- 좋아지는 점: 흔한 지출·수입 질문이 LLM 한 번, 3초 안팎이 됐다. 합계는 서버가 계산한 값이라 틀릴 수 없다.
- 감수할 점: 라우터 출력 칸이 늘어 라우터 한 번이 조금 길어질 수 있다(측정에서 다른 질문의 시간 변화는 흔들림 범위). "식비"가 어느 업종인지는 라우터 규칙에 적은 대로만 해석한다(카페·간식은 넣지 않음). 특정 계좌만·금액 조건이 붙은 검색은 여전히 담당 Agent가 한다.
- 남은 느린 질문: "카드 사용내역"(5번), "체크카드 한도", "생활비 통장 상세", "이체 한도"(4번). 다음 단계는 라우터를 가벼운 모델로 바꿔 모든 질문의 첫 호출을 줄이는 것이다.
