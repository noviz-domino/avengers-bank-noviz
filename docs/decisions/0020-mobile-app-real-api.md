# 0020. 모바일 앱을 실제 API에 연결하고 백엔드가 /app으로 서빙

- 상태: 채택
- 날짜: 2026-11-09
- 관련: [0019 모바일 데모](0019-mobile-demo.md), [모바일 MVP 작업 계획](../design-drafts/NEXT_STEPS.md)

## 배경

0019에서 브라우저 메모리 데모로 화면 흐름을 확인했다. 이제 로그인·계좌·이체 승인·카드·상품·AI 상담을 실제 서버 데이터와 PIN 승인으로 시연해야 하고, 배포 직전 상태까지 만들어야 한다.

## 결정

- `frontend/api.mjs` 하나가 서버 호출을 맡는다: 공통 응답(`data`/`error.code`) 해석, access token 만료 시 refresh 한 번 후 재시도, 세션 만료 알림, 중복 방지 키.
- 토큰은 `sessionStorage`에 둔다(탭을 닫으면 사라짐). 새로고침해도 로그인이 유지된다.
- FastAPI가 `frontend/`를 `/app`에 정적으로 서빙한다. 같은 주소라 API 주소·CORS 설정이 필요 없고 배포 단위가 컨테이너 하나다.
- 개발 중에는 `python -m http.server <포트>`도 쓸 수 있게 CORS에 내 PC 주소(127.0.0.1·localhost의 모든 포트)를 허용한다. 이때 `api.mjs`가 8000번을 부른다.
- 돈 이동은 서버의 승인 대기 → PIN 승인 흐름을 그대로 쓴다. 화면은 서버가 만든 승인 `summary`를 보여 주고, 완료는 서버 실행 성공 뒤에만 표시한다.

## 검토한 대안

| 대안 | 장점 | 비용 |
|---|---|---|
| 프런트 별도 호스팅(Vercel 등) + CORS | 정적 파일 CDN | 배포 대상 둘, 출처별 CORS·쿠키 관리 |
| 토큰을 `localStorage`에 | 탭을 닫아도 유지 | XSS 때 오래 남는 토큰 노출 범위가 큼 |
| httpOnly 쿠키 인증으로 변경 | XSS에 토큰 노출 없음 | 서버 인증 방식·CSRF 대응까지 바꿔야 해 오늘 범위를 넘음 |

## 결과

- 좋아지는 점: 시연 데이터가 서버 DB와 같고, 이체·카드 정지 해제·예금 개설이 실제 PIN 승인을 거친다. 컨테이너 하나로 배포할 수 있다.
- 감수할 점: 토큰이 `sessionStorage`에 있어 XSS 방어(출력 이스케이프)가 중요하다. 백엔드가 없으면 앱이 동작하지 않는다(0019 데모 모드는 독립 화면 테스트용으로만 남김).

## 팀 뼈대와의 차이

- 팀 뼈대는 프런트를 따로 둔다(5173). 이 레포는 백엔드가 `/app`으로 모바일 웹을 같이 서빙한다.
