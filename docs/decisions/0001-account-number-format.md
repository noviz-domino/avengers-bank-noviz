# 0001. 계좌번호 형식과 상품 코드

- 상태: 일부 변경 (→ [0003](0003-db-redesign.md): 계좌 테이블이 하나로 합쳐져 CHECK가 `accounts` 하나로 바뀜. 번호 형식과 상품 코드는 그대로)
- 날짜: 2026-11-04
- 관련 PR: [#1](https://github.com/noviz-domino/avengers-bank-noviz/pull/1)

## 배경

1. **계좌 테이블이 3개다** (`checking_accounts`, `deposit_accounts`, `savings_accounts`). `account_num`의 `unique` 제약은 테이블 하나 안에서만 동작해서, 테이블 사이의 번호 중복은 DB가 막지 못했다. 팀 ERD 문서도 "세 테이블을 모두 검사한다"는 코드 규칙으로만 남겨 두었다.
2. **이체할 때 받는 계좌를 찾으려면** 번호만으로는 어느 테이블인지 몰라서 3번 조회해야 했다.
3. 팀 ERD의 "팀에서 정해야 할 것"에 **계좌번호 형식**이 비어 있었다.

## 결정

### 계좌번호: `110-TPP-NNNNNN`

| 자리 | 뜻 |
|---|---|
| `110` | 은행 코드 (고정) |
| `T` | 계좌 종류: `1` 입출금, `2` 예금, `3` 적금 (`4` 대출 예약) |
| `PP` | 상품 코드 (`account_products.product_code`, 01~99) |
| `NNNNNN` | 일련번호 (000001~999999) |

- 종류 코드가 테이블마다 달라서 **테이블 사이 중복은 구조적으로 불가능**하다.
- 번호만 보고 테이블을 안다 (`account_type_of`). 이체 시 조회 1번.
- 각 계좌 테이블에 **CHECK 제약**: `account_num LIKE '110-1__-______'` (입출금 예시).
- 규칙은 `domains/accounts/account_number.py` 한 곳에 모은다. 번호는 `make_account_num`으로만 만든다.

### 상품 코드: `account_products.product_code` 컬럼 추가

- `SMALLINT NOT NULL`, CHECK `1~99`, `(type, product_code)` unique.
- **종류 안에서만** 고유하다. 입출금 01과 예금 01이 함께 있을 수 있다.

## 검토한 대안

| 대안 | 장점 | 단점 | 고르지 않은 이유 |
|---|---|---|---|
| 랜덤 번호 + 세 테이블 모두 검사 (팀 ERD 원안) | 구조 변경 없음 | 동시에 개설하면 중복 가능, 매번 3번 조회 | DB가 보장하지 못함 |
| 모든 계좌번호를 모은 공통 테이블 | DB가 완전히 보장, 형식 자유 | 테이블 추가, 저장할 때 2번 쓰기 | 종류 코드 방식으로 같은 효과를 더 싸게 얻음 |
| 계좌 테이블을 하나로 합치기 | 거래내역도 한 벌로 끝남 | 팀 ERD와 크게 달라짐 | 지금 문제는 번호 규칙만으로 해결됨. 필요하면 별도 ADR로 |
| PP에 `product_id` 사용 (처음 구현) | 컬럼 추가 없음 | `product_id`는 모든 계좌 상품이 공유하는 자동 증가 값이라 **전체 99개**가 한계, seed를 다시 넣으면 100을 넘어 개설 불가 | PR #1 리뷰에서 발견. 보여주는 번호에 내부 id를 빌려 쓰면 안 됨 |
| CHECK를 PostgreSQL 정규식(`~`)으로 | 숫자까지 DB가 검사 | 테스트용 SQLite에서 동작하지 않음 | 테스트 환경 유지. 숫자는 `make_account_num`이 보장 |

## 결과

**좋아지는 점**
- 테이블 사이 계좌번호 중복을 DB가 막는다.
- 이체할 때 받는 계좌 조회가 1번으로 줄어든다.
- 형식이 틀린 번호(`110-1ab-…`)는 조회 전에 걸러져서 "계좌 없음"이 아니라 "형식 오류"로 안내할 수 있다.

**감수할 점**
- CHECK는 **종류 코드와 길이만** 강제한다. 숫자가 아닌 글자는 `make_account_num`을 거치지 않으면 들어갈 수 있다.
- `alembic check`가 CHECK 변경을 감지하지 못한다. `tests/test_account_number.py`의 `test_migration_checks_match_models`가 모델과 마이그레이션 문구를 비교한다.
- 상품 코드는 종류별 99개, 일련번호는 상품별 999,999개가 한계다.
- 이미 데이터가 있는 DB에 적용하면 실패할 수 있다: 상품이 있으면 `product_code`(NOT NULL) 추가가, 이전 형식의 계좌가 있으면 CHECK 추가가 실패한다. 적용 전에 데이터를 채우거나 비운다.

**아직 정하지 않은 것**
- 일련번호 발급 방식 (DB 시퀀스 추천). 계좌 개설 기능을 만들 때 정한다.
- 동시에 개설할 때 같은 번호가 나오면 생기는 `IntegrityError` 처리.

**팀 뼈대와의 차이**
- `account_products`에 `product_code` 컬럼 추가
- 계좌 테이블 3개에 계좌번호 CHECK 제약 추가
- `domains/accounts/account_number.py` 추가
