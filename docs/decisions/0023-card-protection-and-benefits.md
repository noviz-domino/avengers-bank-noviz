# 0023. 카드 결제 보호(위치·활동시간 확인)와 혜택 구성·주변 코스 상담

- 상태: 채택
- 날짜: 2026-11-11
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0010](0010-card-payments.md) 카드 결제, [ADR 0004](0004-agent-integration.md) 승인, [ADR 0015](0015-agent-chat.md) AI 상담

## 배경

- 카드 결제는 PIN 없이 바로 됩니다(ADR 0010). 카드 번호가 새면 주인이 모르는 결제가 그대로 나갑니다. 주인이 직접 켜는 보호 장치가 필요했습니다.
- 지금 결제 입구(`POST /cards/{id}/payments`)는 카드 주인의 토큰으로 부릅니다. 실제로는 가맹점이 부르는 것이라, "주인 확인이 필요하다"는 판단을 할 자리가 없었습니다.
- 카드 혜택은 상품마다 고정이라, 내 소비에 맞는지 비교하기 어렵습니다. 주변에서 식사·카페를 고를 때 혜택과 쿠폰까지 따져 주는 기능도 없었습니다.

## 결정

### 카드 결제 보호

1. **보호 설정은 `users.card_protection` JSON 한 칸**에 둡니다. 설정(`location_check`, `active_from`, `active_until`), 최근 스마트폰 위치 한 건, 최근 활동·이동 시각만 담습니다. 설정을 바꿀 때는 **거래 PIN**을 받습니다(`PUT /cards/protection`).
2. **가맹점 결제 입구를 시스템 API로 따로 둡니다**: `POST /system/card-payments/{card_id}` (`X-System-Key`). `channel`(`IN_PERSON`·`ONLINE`)을 받고, 오프라인 결제만 단말기 위치를 보냅니다.
3. 결제 규칙(`cards/protection.py` `review_reason`):
   - **오프라인**: 위치 확인을 켰으면 15분 안의 스마트폰 위치가 있어야 하고, 정확도는 2km 이내, 단말기와의 거리는 (거리 − 정확도 − 반올림 여유 800m)가 10km 이하여야 합니다.
   - **온라인**: 활동시간을 정했으면 한국 시간으로 그 안이거나, 5분 안에 은행 화면 활동(`activity_at`) 또는 스마트폰 이동(`movement_at`)이 있어야 합니다. 그리고 50만 원 이상인데 최근 30일 안에 승인된 적 없는 가맹점이면 활동과 상관없이 확인합니다.
4. 규칙에 걸리면 **결제하지 않고 `202` + 승인 대기**(`CARD_PAYMENT`, `requested_by = SYSTEM`)를 만듭니다. 주인이 기존 승인 화면에서 PIN으로 승인하면 그때 결제합니다. 실행 직전에 카드 상태·한도·잔액을 다시 검사합니다(ERD 승인 규칙 3).
5. 가맹점 재전송은 같은 요청 번호로 옵니다. 승인 대기 중이면 같은 대기를 `202`로, 결제가 끝났으면 그 결제를 `200`으로, 거절·만료·실패였으면 `409 CARD_PAYMENT_NOT_APPROVABLE`로 답합니다.
6. 보호를 켠 사용자는 기존 `POST /cards/{id}/payments`로 결제할 수 없습니다(`409 MERCHANT_CHANNEL_REQUIRED`). 보호를 피해 가는 입구를 남기지 않습니다.
7. 위치는 **브라우저가 보낸 좌표를 소수 둘째 자리(약 1km)로 반올림해 한 건만** 저장합니다. 위치 확인을 끄면 저장한 위치를 지웁니다. 위치 좌표는 조회 API로 돌려주지 않습니다.
8. 카드 사용내역에 `payment_date`(한국 날짜) 조건을 추가했습니다. AI 상담이 "어제 모르는 결제"를 찾을 때 씁니다.

### 혜택 구성과 주변 코스

1. **혜택 카탈로그는 은행 코드에 고정**합니다(`products/benefits.py` `CATALOGUE`, 6개). 사용자는 그 안에서 **100크레딧 이내, 업종마다 하나**를 고릅니다. 고른 `offer_id` 목록만 `users.benefit_bundle`에 저장합니다.
2. 저장한 구성은 **미리보기**입니다. 실제 카드 결제 금액에는 적용하지 않습니다.
3. 추천은 최근 완료된 3개월의 내 카드 승인 내역을 업종(카페·식사·교통·편의점)으로 묶어, 월 할인 한도를 반영한 예상 할인이 가장 큰 조합을 **코드가 계산**합니다. AI는 그 결과를 설명만 합니다.
4. 주변 코스는 카카오 로컬 API로 1.5km 안 식당·카페를 찾고, 현재 위치 → 식당 → 카페 → 현재 위치의 예상 시간과 금액을 계산해 가장 빠른 코스와 가장 싼 코스를 돌려줍니다. 키(`KAKAO_LOCAL_API_KEY`)가 없으면 예시 매장으로 시연합니다.
5. 상담은 `POST /chat/benefits` 하나입니다. 도구는 읽기 전용이고, 응답에 AI의 말과 함께 **도구가 계산한 원본 결과**(`recommendation`·`plan`)를 붙입니다.

### 송금 전 요청 점검

- `POST /chat/transfer-check`는 받은 문자·요청을 내 과거 송금과 비교하는 **읽기 전용** 상담입니다. 도구는 `compare_previous_transfers` 하나이고, 계좌번호는 끝 4자리만 돌려줍니다. 이체 도구가 없어서 송금을 만들 수 없습니다.

## 검토한 대안

### 의심 결제를 어떻게 처리할까

| 대안 | 장점 | 단점 | 고르지 않은 이유 |
|---|---|---|---|
| 의심 결제는 바로 거절 | 단순함 | 주인이 해외·출장 중이면 결제가 안 됨 | 오탐 비용이 큼 |
| 결제 후 알림만 | 실제 카드사에 가까움 | 돈이 이미 나감 | 보호가 되지 않음 |
| **승인 대기 후 PIN 승인** | 기존 승인 화면·재검사·만료를 그대로 씀 | 가맹점이 202를 받고 다시 보내야 함 | **채택** |

### 보호 설정을 어디에 둘까

| 대안 | 장점 | 단점 | 고르지 않은 이유 |
|---|---|---|---|
| 별도 테이블(`card_protection_settings`, `phone_locations`) | 컬럼 단위 제약 | 테이블 두 개, 위치 이력이 쌓임 | 위치는 한 건만 필요해 과함 |
| **`users`에 JSON 한 칸** | 마이그레이션 한 줄, 사용자 행 잠금으로 갱신 직렬화 | DB가 내용 형식을 검사하지 못함 | **채택**. 읽을 때 Pydantic으로 검증 |

### 혜택 할인율을 누가 정할까

| 대안 | 장점 | 단점 | 고르지 않은 이유 |
|---|---|---|---|
| AI가 소비를 보고 할인율·조합을 제안 | 유연함 | 은행이 승인하지 않은 할인이 나올 수 있음 | 숫자를 AI에 맡기지 않음 |
| **은행 카탈로그 + 코드 계산, AI는 설명** | 저장·응답 숫자가 항상 카탈로그와 같음 | 카탈로그를 코드로 고쳐야 함 | **채택** |

## 결과

**좋아지는 점**
- 카드 번호만 가진 사람이 다른 지역·다른 시간에 결제하면 주인 PIN 없이는 돈이 나가지 않습니다.
- 의심 결제 처리에 새 승인 경로를 만들지 않고 `pending_actions`와 실행 직전 재검사를 그대로 씁니다.
- 혜택 구성과 코스 금액은 코드가 계산하고 응답에 원본이 붙어서, AI의 말과 숫자가 다르면 화면에서 바로 보입니다.

**감수할 점**
- 위치와 활동은 로그인한 은행 화면(브라우저)이 보내는 값이라 기기를 신뢰할 근거가 없습니다(코드의 `shortcut` 주석). 실결제망에 붙이려면 기기 인증이 필요합니다.
- 가맹점 비교는 이름으로 합니다. 실제로는 가맹점 ID를 써야 합니다.
- 승인 대기는 10분 뒤 만료되고, 만료된 결제는 같은 번호로 다시 보내도 `409`입니다. 가맹점이 새 번호로 다시 결제해야 합니다.
- `card_protection`·`benefit_bundle`은 JSON이라 DB CHECK로 형식을 막지 못합니다. 카탈로그가 바뀌어 저장된 구성이 맞지 않으면 빈 구성과 `needs_review: true`를 돌려줍니다.
- 주변 코스의 가격은 사용자가 넣은 예상 가격(시연은 예시 가격)이고, 시간은 직선 거리 × 1.25를 분당 70m로 나눈 추정치입니다. 쿠폰 파일(`benefit_coupons.json`)은 지금 비어 있습니다.
- downgrade는 `SYSTEM` 승인 대기가 남아 있으면 이전 CHECK를 다시 만들 수 없어 실패합니다.

**팀 뼈대와의 차이**
- 팀 뼈대: 카드 결제 보호·혜택 구성 없음 → 이 레포: `users.card_protection`, `users.benefit_bundle` JSON 칸 추가, `pending_actions.requested_by`에 `SYSTEM` 추가, 승인 종류 `CARD_PAYMENT` 추가
- 가맹점 결제 시뮬레이터 `POST /system/card-payments/{card_id}` 추가 (기존 `POST /cards/{id}/payments`는 보호를 켜지 않은 사용자만)
