# 0005. 인증 구조: 로그인과 거래 인증(PIN → 패스키)

- 상태: 제안 (이 PR에서 리뷰)
- 날짜: 2026-11-04
- 관련 PR: #4

## 결정

인증을 **두 단계**로 나눈다.

| 단계 | 묻는 것 | 이 레포에서 |
|---|---|---|
| ① 로그인 | 누구세요 | 아이디·비밀번호 + **5회 실패 시 잠금** + **access token(짧게) / refresh token(쓸 때마다 새로 발급, 로그아웃 시 폐기)** |
| ② 거래 인증 | 이 거래를 지금 본인이 승인하나 | **1차: 거래 PIN(6자리)**, **2차: 패스키(WebAuthn)** 추가. PIN은 대체 수단으로 유지 |

- ②는 `pending_actions` 승인에 쓴다(ADR 0004). 로그인 토큰만으로는 돈을 움직일 수 없다.
- PIN과 refresh token은 **비밀번호처럼 해시로만 저장**한다.
- 잠금은 둘로 나눈다: 로그인 5회 실패 → `login_locked_until`, PIN 5회 실패 → `pin_locked_until`. **PIN을 틀려도 로그인은 잠기지 않는다**(토큰을 가진 Agent가 사용자를 쫓아내지 못하게). 각 실패 횟수는 성공하면 0으로 돌아간다.
- 로컬 MCP는 refresh token으로 access token을 받아 쓴다(ADR 0004).
- **휴대폰 본인확인은 하지 않는다.** 회원가입 때 휴대폰 번호는 입력만 받는다.

## 배경

- 실제 은행의 공동인증서·금융인증서·PASS 본인확인은 **기관 계약**이 필요해서 쓸 수 없다.
- 이 레포는 Agent에게 사용자 토큰을 넘긴다(ADR 0004). 그래서 **"토큰을 가진 것"과 "사람이 지금 승인한 것"을 구분하는 장치**가 꼭 필요하다. 그게 ② 거래 인증이다.
- 패스키(WebAuthn, FIDO2)는 실제 은행 앱의 생체 인증과 **같은 국제 표준**이고, 무료 라이브러리(`webauthn`, `@simplewebauthn/browser`)로 구현할 수 있다.

## 검토한 대안

### 거래 인증

| 대안 | 결과 |
|---|---|
| 없음 (로그인만) | 토큰이 Agent나 공격자에게 넘어가면 바로 이체됨. 버림 |
| 로그인 비밀번호 재입력 | 은행 앱의 실제 흐름과 다르고, 비밀번호가 자주 노출됨 |
| **거래 PIN** | 실제 은행의 "간편 비밀번호". 단순. 다만 사용자가 PIN을 Agent에게 알려주면 뚫림. **1차로 채택** |
| **패스키** | 기기 안의 키로 서명. Agent는 기기와 지문을 가질 수 없어서 **사람이 승인했다는 것을 암호학적으로 증명**. **2차로 채택** |
| OTP 앱 | 별도 앱이 필요해서 데모하기 어려움. 버림 |

### refresh token

| 대안 | 결과 |
|---|---|
| access token 하나만 오래 (팀 뼈대: 30분) | 로그아웃해도 토큰이 살아 있음. 버림 |
| **짧은 access + DB에 저장한 refresh, 쓸 때마다 교체** | 로그아웃·기기별 로그아웃 가능. 이미 쓴 refresh가 다시 오면 **도난으로 보고 그 계열 전체 폐기**. **채택** |

### 휴대폰 본인확인

| 대안 | 결과 |
|---|---|
| 실제 문자 발송 (외부 SMS 서비스) | 비용·가입 필요. 버림 |
| 모의 코드 (화면에 코드 표시) | 흐름은 실제와 같지만 실제로 아무것도 확인하지 않아서 **포트폴리오에서 보여줄 가치가 낮고**, 회원가입만 길어짐. 버림 |
| **하지 않음** | **채택**. 비밀번호 찾기도 범위 밖 |

## 결과

**좋아지는 점**
- "로그인했다"와 "이 거래를 승인했다"가 분리돼서, **토큰이 새도 돈은 움직이지 않는다.**
- 패스키가 붙으면 "Agent는 사람의 기기와 지문을 가질 수 없다"를 실제로 보여줄 수 있다.
- TIL에서 배운 인증·인가에 **단계별 인증(step-up)**이 더해진다.

**감수할 점**
- 패스키는 **HTTPS + 정해진 도메인**에서만 동작한다(로컬은 `localhost`로 가능). 배포 도메인(RP ID)을 일찍 정해야 하고, 바뀌면 등록된 패스키를 못 쓴다.
- 데모를 보는 사람 기기가 패스키를 지원하지 않을 수 있어서 PIN을 대체 수단으로 남긴다.
- 6자리 PIN은 경우의 수가 백만 개뿐이라 **실패 횟수 제한이 필수**다.
- 휴대폰 번호가 실제 본인 것인지 확인하지 않는다. 비밀번호를 잊으면 복구할 방법이 없다(데모 계정은 seed로 다시 만든다).

**팀 뼈대와의 차이**
- `users`에 생년월일, 마케팅 동의, 거래 PIN 해시, 실패 횟수, 잠금 시각(로그인·PIN 따로) 추가
- `refresh_tokens`(보안 보강 때), `passkeys`(2차) 추가
- 로그인 응답이 access token 하나에서 access + refresh로 바뀜
