# 0033. 되돌릴 수 없는 일(계좌 해지·분실 확정)도 PIN 승인 뒤에: 분실 신청은 카드를 바로 멈춤

- 상태: 채택
- 날짜: 2026-11-26
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0004(AI 연결 구조)](0004-agent-integration.md) 승인 원칙, [ADR 0012(계좌 해지)](0012-account-close.md) 계좌 해지 조건, [ADR 0014(MCP 서버)](0014-mcp-server.md) MCP 도구, [ADR 0030(카드 상태 감사 기록)](0030-card-status-audit-demo-card.md) 카드 상태 감사 기록

## 배경

- 지금까지 PIN 승인은 "돈이 움직이거나 위험해지는 쪽"에만 걸었습니다. 계좌 해지(잔액 0)와 카드 분실 신고는 돈이 움직이지 않아 바로 실행했고, AI 상담과 MCP 도구에서는 "사용자가 확인한 뒤에만 부르라"는 **지시문**만 막고 있었습니다.
- 그런데 둘 다 **되돌릴 수 없습니다.** 해지한 계좌는 목록에서 사라지고, 분실 카드는 다시 쓸 수 없어 재발급해야 합니다. 모델이 지시를 어기거나 도구 결과 속 지시문에 속으면 사람이 확인하지 않은 채 실행됩니다(ADR 0030(카드 상태 감사 기록)의 "어느새 분실된 데모 카드"가 실제로 있었던 일).
- 서버는 입구(화면·AI·MCP)를 `X-Requested-By` 헤더로 구분하지만 이 값은 클라이언트가 보내는 **정보용**입니다. 입구별로 다르게 막으면 헤더를 `WEB`으로 보내는 것만으로 피할 수 있습니다. 그래서 막는다면 모든 입구에 똑같이 걸어야 합니다.
- 반대로 카드 **일시정지**는 되돌릴 수 있고, 카드를 잃어버린 사람에게는 "지금 당장 멈추는 것"이 가장 중요합니다. 여기에 PIN을 걸면 급할 때 늦어집니다.

## 결정

1. **계좌 해지는 승인 대기만 만든다** (`POST /accounts/{id}/close` → `202`, `CLOSE_ACCOUNT`, 본문 `idempotency_key`). 해지 조건(ADR 0012(계좌 해지))을 신청 때 미리 검사해 바로 알려 주고, PIN 승인 때 **같은 검사**(`lock_closable`)를 다시 한 뒤 해지한다(`run_close_account`). 그사이 돈이 들어왔거나 카드가 생겼으면 해지하지 않고 `FAILED`로 남긴다.
2. **분실 신고는 두 단계로 나눈다** (`POST /cards/{id}/report-lost` → `202`, `REPORT_LOST`). 신청하면 카드를 **바로 일시정지**하고(감사 기록 `CARD_SUSPENDED`, `why: REPORT_LOST`), 되돌릴 수 없는 **분실 확정**은 PIN 승인 뒤에 한다(`run_report_lost`, 감사 기록 `CARD_LOST`, `actor=USER`, 요청 입구는 `detail.requested_by`). 승인을 취소하면 카드는 일시정지 상태로 남아 정지 해제(PIN)로 되살릴 수 있다. 분실 신청이 대기 중인 카드는 정지 해제를 신청할 수도, 이미 만든 해제 요청을 승인할 수도 없다(`CARD_LOST_PENDING`). 잃어버린 카드가 분실 확정 전에 다시 결제되지 않게.
3. **`POST /cards/{id}/suspend`는 일시정지만 받는다**(`reason: SUSPENDED`). `LOST`를 보내면 `422`.
4. **AI·MCP 도구 이름을 바꾼다**: `close_account` → `request_close_account`, `suspend_card(lost=true)` → `request_report_lost_card`. 해지 요청은 승인 대기만 만들어 `destructiveHint=false`, 분실 신청은 카드를 바로 멈춰서 `destructiveHint=true`(`suspend_card`와 같음). `suspend_card`는 일시정지만. AI 상담 화면은 이번 턴에 이름이 `request_`로 시작하는 도구가 돌면 승인 대기를 찾아 승인 카드를 붙이므로(`frontend/chat.mjs`) 화면 코드는 바꾸지 않는다.
5. **화면도 같은 승인 창을 쓴다**: 계좌 관리의 "PIN으로 해지하기", 카드 관리의 "분실 신고"가 공통 PIN 창(`approval.mjs`)을 연다.

## 검토한 대안

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| AI·MCP 입구에서만 승인 | 화면 흐름이 그대로 | 입구 구분 헤더는 클라이언트가 보내는 값이라 `WEB`으로 보내면 피함. 안전장치가 아니라 안내문이 됨 |
| 분실 신고 전체를 PIN 뒤로 | 단순 | 카드를 잃어버린 순간 PIN 창을 거쳐야 카드가 멈춤. 일시정지는 되돌릴 수 있으니 바로 하는 게 맞음 |
| 지시문만 더 강하게 | 코드 변경 없음 | 모델이 지시를 어기면 막을 방법이 없음 (ADR 0030(카드 상태 감사 기록)의 실제 사례) |
| 카드 일시정지도 PIN | 모든 상태 변경이 같은 규칙 | 안전해지는 쪽을 늦춤 (ADR 0004(AI 연결 구조) 원칙과 반대) |

## 결과

- 좋아지는 점: 되돌릴 수 없는 일은 어느 입구든 사람이 PIN을 넣어야 일어납니다. 모델이 잘못 불러도 카드는 일시정지까지만 되고 계좌는 그대로입니다. 분실 신청 때 카드가 바로 멈춰서 급할 때도 느려지지 않습니다.
- 감수할 점: 해지와 분실 신고가 화면에서 한 단계(PIN) 늘어납니다. `POST /accounts/{id}/close`의 응답이 계좌 상세에서 승인 대기로 바뀌고 본문에 `idempotency_key`가 필요해서, 이 API를 직접 부르던 클라이언트는 고쳐야 합니다(이 레포의 화면·MCP·테스트는 함께 고침).
- 이전 결정과의 관계: ADR 0004(AI 연결 구조)의 "안전해지는 쪽은 바로" 원칙은 일시정지에 그대로 남고, ADR 0012(계좌 해지)의 "잔액 0이면 바로 해지"와 ADR 0014(MCP 서버)의 `close_account`·`suspend_card(lost)` 도구는 이 문서로 바뀝니다.
