# 0034. AI 상담 빠른 길: 단순 조회는 라우터 한 번 + 도구 + 코드가 쓴 답

- 상태: 채택
- 날짜: 2026-11-27
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0016(응답 시간 측정)](0016-agent-latency-tracing.md) 응답 시간 측정, [ADR 0018(채팅 스트리밍)](0018-chat-stream-router.md) 라우터·스트리밍, [ADR 0006(에이전트 구조)](0006-agent-orchestration.md) "다시 검토할 조건"(p95 8초)

## 배경

- 한 턴은 라우터(LLM 1번) → 담당 Agent가 도구 고르기(1번) → 도구 → 담당이 답 쓰기(1번)로 최소 LLM 세 번이 든다. 한 번이 3~4초라 "잔액 알려줘"도 10초 안팎이었다(개선 전 측정 p50 11.3초).
- 잔액·카드 목록·남은 예산은 도구 하나로 끝나고 답 모양도 정해져 있다. 담당 LLM 두 번은 "이 도구를 부르자"와 "결과를 문장으로"뿐이다.
- 약관 질문은 상품 담당이 `ask_bank_docs`(RAG)를 부르고 RAG의 답을 다시 문장으로 옮긴다. RAG가 근거와 함께 이미 답을 쓴다.
- 이전 프로젝트(노비즈 뱅크)는 LLM 한 번으로 의도와 값을 정하고 코드가 실행과 답을 맡아 빨랐다. 그 장점만 가져온다.

## 결정

1. **라우터의 한 번 호출에 `quick` 표시를 더한다** (`Plan.quick`, `Plan.question`). 담당을 고르면서 그 담당의 일이 아래처럼 단순한지도 함께 표시한다. 조건·기간·특정 계좌만·금액이 붙거나 확실하지 않으면 표시하지 않는다.
   - `balance`(계좌): 잔액·총자산·계좌 목록 전체 → `get_my_accounts`
   - `cards`(카드): 카드 목록·상태 → `get_my_cards`
   - `budget`(예산): 이번 주기 더 쓸 수 있는 돈·하루 쓸 돈 → `get_budget` (금액이 있는 "X원 써도 돼?"는 아님)
   - `docs`(상품): 약관·규칙·상품 조건 질문 → `ask_bank_docs`(라우터가 앞 대화 없이도 알 수 있게 다시 쓴 `question`)
2. **담당 노드 안에서 처리한다** (`agent/quick.py`의 `run_lane`). 표시가 있으면 담당 LLM 없이 도구를 바로 부르고 코드 템플릿으로 답을 쓴다. 노드 이름·`routed`·진행 표시(담당 → 도구)가 그대로라 화면과 평가 스크립트를 바꾸지 않는다. 복합 요청("잔액이랑 예산")도 담당마다 따로 빠른 길을 탄다.
3. **도구가 실패하면 원래 길로**: 서버 오류나 RAG 꺼짐이면 `None`을 돌려주고 담당 Agent가 평소처럼 처리한다. 빠른 길은 답을 빠르게 할 수는 있어도 나빠지게 하지 않는다.
4. **이체·검색·한도처럼 값을 골라야 하는 일은 그대로 담당 Agent**가 한다. 돈이 움직이는 일은 지금처럼 승인 대기 + PIN이다.

## 측정 (2026-11-27, gemini-3.8-flash, 생각 low, 데모 계정, 같은 질문 21개, 한 번씩)

|---|---|---|---|---|

| **빠른 길** | **21/21** | **2.4** | **8.7초** | **15.9초** |

- 측정 원본과 질문별 전후 표: [평가 기록](../evaluations/agent-latency/README.md). 다음 단계 근거: [조사 보고서](../research/agent-latency-and-rag.md)
- 질문당 LLM 호출은 Agent 쪽만 센다. 약관 질문의 RAG 답변 호출(서버 안의 Gemini 한 번)은 전후 모두 세지 않았다.
- p95는 여전히 검색형 질문("이번 달 식비 얼마 썼어?" 5번, "카드 사용내역" 5번)이 끌어올린다. 기간·업종을 골라야 해서 빠른 길에 넣지 않았다.

## 검토한 대안

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 라우터를 더 가벼운 모델로 | 라우터 한 번이 빨라짐 | 줄어드는 것은 1초 안팎. 담당 호출 두 번을 없애는 쪽이 훨씬 큼. 측정 뒤 다시 |
| 노비즈 뱅크처럼 모든 일을 LLM 한 번 + 코드로 | 가장 빠름 | 담당 4개의 도구 19개를 한 스키마에 넣으면 고르기가 거칠어짐(ADR 0006(에이전트 구조)). 모양이 정해진 조회만 |
| 이체도 빠른 길(슬롯 채우기) | 이체 요청이 빨라짐 | 내 계좌 이름을 라우터 스키마에 넣어야 하고, 모호하면 되묻기가 필요. 다음 단계 후보 |
| 검색형 질문 빠른 길 | p95를 낮춤 | 기간·업종·키워드를 라우터가 채워야 함. 다음 단계 후보 |

## 결과

- 좋아지는 점: 가장 흔한 단순 조회가 3초 안팎이 됐다. 템플릿이 서버 숫자를 그대로 옮겨 예산 담당 프롬프트의 "계산하지 마라" 같은 위험이 이 길에는 없다.
- 감수할 점: 템플릿 답은 고정된 말투다. 잔액 질문이 "생활비 통장만"이어도 라우터가 표시하면 전체 목록이 나온다(규칙에서 "특정 계좌만"은 표시하지 말라고 적어 둠). 템플릿 답은 글자 단위로 흐르지 않고 끝에 한 번에 온다(빨라서 체감 차이가 적음).
- 여전히 ADR 0006(에이전트 구조)의 기준(p95 8초)은 넘는다. 다음 후보: 검색형 질문과 이체의 빠른 길, 라우터 경량 모델.
- 측정은 한 번씩이라 p95는 가장 느린 1~2개다. 결론은 경향으로 본다.
