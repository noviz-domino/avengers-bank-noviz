# 0002. 예산 관리 추가와 구현 범위 조정

- 상태: 채택 (일부 항목은 "결정 대기")
- 날짜: 2026-11-04
- 관련 PR: [#2](https://github.com/noviz-domino/avengers-bank-noviz/pull/2)

## 결정

1. **예산 관리 기능을 추가한다.** 월급날까지 "자유롭게 쓸 수 있는 돈"을 계산하고, 그 돈을 넘는 결제는 사용자가 직접 확인해야만 실행한다. 명세: [budget.md](../planning/budget.md)
2. **구현 범위를 포트폴리오 기준으로 정한다.** 돈 처리·보안·예산 관리·자연어 Agent를 깊게, **대출(16개 중 9개)을 포함한 나머지는 가볍게** 만든다. 범위: [scope.md](../planning/scope.md)
3. **모든 지출은 쓴 주기에서 한 번만 차감한다.** 신용카드도 쓴 순간 차감하고, 카드 대금 출금·목표 저축 이체·내 계좌끼리의 이동은 차감하지 않는다.
4. **예산 초과 결제의 확인은 사람만 할 수 있다.** 자연어 Agent의 도구에 확인 API를 넣지 않는다.

## 배경

- 이 레포는 포트폴리오로 쓴다. 팀 기획 41개를 얕게 다 만들면 이전 포트폴리오(langgraph-financial-agent)와 비슷한 "은행 Agent"로 보인다.
- 이전 프로젝트는 JSON 장부를 다뤘다. 이번에는 실제 DB·인증·트랜잭션이 있어서, **돈 처리의 정확성**과 **Agent를 실제 백엔드에 안전하게 붙이는 것**을 보여줄 수 있다.
- 차별 기능이 필요했다. 소비 분석 서비스는 많지만 대부분 **분석과 알림까지**다. 은행은 **결제 순간에 개입**할 수 있다.

## 검토한 대안

### 신용카드를 예산에 넣는 방식

| 대안 | 장점 | 단점 | 결과 |
|---|---|---|---|
| 고정 지출에 "카드값"을 적고 결제 때도 차감 | 직관적 | **같은 돈을 두 번 차감** | 버림 |
| 이번 달 사용액을 **다음 달 예산**에서 차감 | 실제 돈이 나가는 시점과 같음 | 결제 수단마다 "어느 달"인지 달라 복잡. 신용카드 결제 검사 때 다음 달 예산을 미리 계산해야 함 | 버림 |
| **쓴 순간 이번 주기에서 차감하고 "청구 예정"으로 묶어 둠** | 규칙이 하나("모든 지출은 쓴 주기에서 한 번만"). 카드 결제일이 언제든 동작 | 화면에 "청구 예정 금액"을 따로 보여줘야 함. 카드 대금 출금을 거래내역에서 구분해야 함(`CARD_BILL`) | **채택** |

### 목표 저축을 옮기는 시점

| 대안 | 결과 |
|---|---|
| 월급날 바로 적금으로 이체 | 주기 중간에 생활비가 모자라도 되돌릴 수 없고, 이체한 돈을 "아직 안 모은 저축"으로 또 빼면 이중 차감이 됨 (PR #2 리뷰). 버림 |
| 예산에서 떼어두기만 (가상) | 실제 돈이 움직이지 않아 은행 앱답지 않음 |
| **주기 시작에 묶어 두고 주기 끝에 적금으로 이체** | 신용카드와 같은 "묶어 두기" 방식으로 통일. 부족하면 묶음을 풀 수 있음. **채택 (추천안, 결정 대기)** |

### 예산 주기

| 대안 | 결과 |
|---|---|
| 달력 기준 (1일~말일) | 월급날이 25일이면 월말에 돈이 몰리고 월초에 모자람. 버림 |
| 월급 **입금** 시점 기준 | 월급이 하루 늦으면 주기가 흔들림. 버림 |
| **등록한 월급날 날짜 기준**, 실제 입금액으로 수입만 갱신 | **채택** |

### 필수 생활비 계산

| 대안 | 결과 |
|---|---|
| 필수 카테고리 "식비" 하나에 회식까지 포함 | 회식은 필수가 아님 (PR #2 리뷰). 버림. **식사(필수)와 외식·술자리(선택)로 나눔** |
| 하루 평균 | 튀는 달에 크게 부풀어서 버림 |
| 하루 단위 중앙값 | 지출이 없는 날이 많은 카테고리는 0이 됨 (PR #2 리뷰). 버림 |
| 최빈값 | 금액이 같은 값으로 거의 반복되지 않아 구간으로 묶어야 하고, 묶는 폭에 따라 결과가 달라짐. **계산에는 쓰지 않고 "가장 자주 쓰는 금액대" 표시에만 사용** |
| **카테고리별 주기 합계의 중앙값 × 남은 일수 비율** | 지출이 드문 날·주말 차이를 흡수. **채택**. 화면에는 보통 범위(하위 25%~상위 25%)도 표시 |

의료·약국처럼 가끔 쓰는 필수 지출은 미리 떼어 두지 않고 결제 때 항상 통과시킨다. 월세·통신비처럼 금액이 일정한 것은 필수 생활비가 아니라 **고정 지출**로 따로 관리하고, 분석이 반복 결제를 찾으면 고정 지출로 추천한다.

### 예산 초과 결제

| 대안 | 결과 |
|---|---|
| 무조건 거부 | 긴급한 일이나 병원비·약값까지 막힐 수 있음. 버림 |
| 알림만 | 개입이 약해서 차별점이 없음 |
| **확인 요청 (사유를 적고 확인하면 다시 검사 후 결제)**, 필수 업종과 "긴급" 사유는 통과 | **채택 (추천안)**. 이전 포트폴리오의 승인 패턴과 같은 구조 |

### 확인을 누가 할 수 있나

| 대안 | 결과 |
|---|---|
| 사용자 토큰을 가진 누구나 (Agent 포함) | Agent가 사유를 스스로 채워 확인할 수 있어서 **결제 순간의 개입이 Agent 경로에서 무력해짐** (PR #2 리뷰). 버림 |
| **확인 번호를 확인 화면에서만 보여주고, Agent 도구에는 확인 API를 넣지 않음** | **채택**. Agent는 확인 화면 링크만 안내 |

### 범위

| 대안 | 결과 |
|---|---|
| 팀 기획 41개 전부 | 혼자 깊게 만들기 어려움. 버림 |
| 대출 전부 빼기 (처음 초안) | 은행 앱의 대표 기능이 빠짐 (PR #2 리뷰). 버림 |
| **대출을 가볍게: 16개 중 9개** (조회·한도·신청·자동 심사·실행·계좌 조회·이자와 상환 일정·상환) | 서류·연체·중도상환 등 7개는 뺌. 상환액은 예산의 고정 지출에 자동 등록. **채택** |
| 영업점 우대(지점장 승인 금리) 구현 | 직원 역할·관리자 화면이 필요. **자리만 남김**(`source=BRANCH`, `approved_by`) |

## 결과

**좋아지는 점**
- 이 프로젝트만의 이야기가 생긴다: "결제 순간에 다음 월급날까지 현금 흐름을 예측해서 개입하고, 그 확인은 AI가 아니라 사람이 한다."
- 이체에서 만드는 행 잠금·멱등키가 카드 결제·예산 검사에서 그대로 쓰여서, 돈 처리 로직이 한 곳에 모인다.
- 신용카드와 목표 저축이 같은 "묶어 두기" 방식이라 규칙이 하나로 정리된다.
- 저축 목표, 자동이체, 대출 상환 같은 팀 기획 기능이 예산 관리와 이어진다.

**감수할 점**
- 거래내역·카드 사용내역에 **카테고리**와 **거래 종류**(`CARD_BILL`, `GOAL_SAVING`, `INTERNAL`)가 필요하다. 팀 ERD에 없어서 테이블 변경이 생긴다.
- 결제마다 사용자의 주기 행을 잠가서, 한 사용자의 결제는 동시에 처리되지 않고 하나씩 처리된다. 개인 사용자 기준으로는 문제없는 수준이다.
- 분석 화면을 데모로 보여주려면 **6개월치 가상 거래 데이터**가 필요하다.
- 범위가 팀 기획과 달라서, 매일 아침 공유 때 차이를 설명해야 한다. 이 ADR과 `scope.md`의 "팀 기획과의 차이"로 설명한다.

**결정 대기** (추천안으로 기획, 구현 전 확인)
- 예산 초과 시 방식: 확인 모드 하나로 시작할지, 알림·잠금 모드도 만들지
- 목표 저축: 주기 끝 적금 이체(추천) / 월급날 이체 / 가상
- 검사 대상: 계좌 이체까지 포함할지
- 주기 끝에 남은 돈: 이월할지
- 6개월 데모 데이터 seed 준비 여부

**팀 뼈대와의 차이**
- 예산 관리 테이블 6개 추가 예정 (`budget.md`의 "필요한 데이터")
- 입출금 거래내역 type에 `CARD_BILL`, `GOAL_SAVING`, `INTERNAL` 추가 예정
- 대출은 팀 기획 16개 중 9개만
