# 0024 — 예산 계산과 사람의 결제 확인

- 상태: 채택, 로컬 구현·검증 완료 (미커밋)
- 날짜: 2026-11-09

## 배경

[예산 기획](../planning/budget.md)의 자유 사용 가능액을 이체·카드 결제와 AI 상담에서 같은 기준으로 사용한다. 중단된 작업의 변경분을 현재 통합 브랜치에 복구했다.

## 결정

- 월급날부터 다음 월급날 전날까지를 주기로 삼는다. 수입에서 지출, 아직 안 낸 고정 지출, 남은 날의 필수 생활비, 목표 저축을 뺀다. 금액은 정수 원이다.
- `budget_profiles`, `fixed_expenses`, `budget_cycles`, `budget_decisions` 네 테이블을 추가한다. 목표는 현재 프로필에 한 개만 둔다.
- 목표 네 필드의 일부만 NULL인 행은 CHECK로 막는다. 이미 예산 테이블이 생성된 DB에도 적용되도록 후속 마이그레이션 `a61d9e72b4c8`에서 제약을 교체한다.
- 타인 이체와 체크·신용카드 결제를 검사한다. 내부 이체와 카드 대금은 중복 지출로 세지 않는다.
- 예산 초과 카드 결제는 `409 BUDGET_CONFIRMATION_REQUIRED`와 승인 번호를 반환한다. 이체는 기존 PIN 승인에 예산 영향과 필수 사유를 추가한다. 실행 시 다시 검사하며 확인 때보다 악화됐으면 실패한다. 긴급 선택은 사유와 함께 기록한다.
- 항상 통과 업종은 서버가 가맹점명으로 분류한 카드 결제에만 적용한다. 통과하더라도 지출과 결정 기록에 남긴다.
- 해지와 검사 완화는 기존 승인 대기 후 PIN으로 처리한다. `PATCH /budget` 강화는 200 요약을, 완화는 202 `BUDGET_UPDATE` 승인 요청을 반환한다. 수입 증가·필수 생활비 감소/삭제·고정 지출 감소/삭제/날짜 변경·목표 저축 감소/삭제·항상 통과 업종 추가가 완화다. 승인 화면의 서버 요약에 실제 변경값을 표시하며, 승인 전 설정이 달라졌으면 `BUDGET_CHANGED`로 실패하여 새 요청을 받는다. 고정 지출 이름은 중복을 금지한다.
- 카드 행 → 예산 주기 → 계좌 순서로 잠근다. 이체는 카드 행 없이 주기 → 계좌 순서다. SQLite 테스트는 PostgreSQL 행 잠금의 동시성 증거가 아니다.
- AI 도구는 `get_budget`, `check_budget` 조회 두 개뿐이다. AI는 서버 숫자를 인용하며 신청·변경·해지·초과 결제 승인을 수행하지 않는다. 이미 쓴 돈은 계좌 담당, 앞으로 쓸 돈은 예산 담당으로 라우팅한다.

## 검토한 대안

별도 예산 승인 API 대신 기존 승인 수명주기와 PIN 검증을 재사용한다. 목표별 테이블과 자동 분석은 현재 실행 검증에 필요하지 않아 추가하지 않았다.

## 결과와 남은 범위

계산·확인·실행 재검사를 공통 서버 코드로 처리한다. 신청·조회·수정·해지 화면과 홈 요약을 연결했다. 실제 Gemini 예산 답변, 라우팅 평가, PostgreSQL 동시 결제를 확인했다. 둘째 주기 분석, 이월, 목표 자동 이체는 후속 범위다. 상세 검증은 [복구 상태](../design-drafts/RESUME_STATUS.md)에 기록한다.

팀 뼈대에는 예산 도메인과 예산 담당 Agent가 없으며 이 구현이 추가한다.

## 타행 이체·결제 보호와 합친 뒤 (2026-11-11)

예산은 [0022](0022-clearinghub.md) 타행 이체와 [0023](0023-card-protection-and-benefits.md) 결제 보호보다 늦게 main에 들어왔다. 세 기능이 같은 승인 실행(`approvals/service.py`)과 카드 결제(`cards/service.py`)를 지나서 다음처럼 맞췄다.

- 카드 결제는 실행 함수 하나(`_execute_payment`)가 한도·신용·예산을 검사한다. 바로 결제, 보호 승인 뒤 결제, 예산 확인 뒤 결제가 모두 이 함수를 지난다.
- 결제 보호가 결제를 보류할 때 예산도 미리 계산해 같은 승인 화면에 영향 문장을 붙인다. 넘으면 그 승인에서 사유를 받는다. 이체와 같이 PIN 한 번으로 두 확인을 받는다.
- 승인 뒤 실행할 때는 나빠졌는지만 본다. 보호 승인 사이에 예산을 새로 넘게 되면 승인 안에서 새 확인을 만들 수 없어서 `BUDGET_CHANGED`로 실패시키고 돈은 움직이지 않는다.
- 같은 결제 요청 번호의 재전송은 결제 내용만 비교한다. 예산 숫자는 그사이 바뀔 수 있어서 비교에서 뺀다.
- 타행 이체에는 아직 예산 가드를 붙이지 않았다. 실행 함수 `clearing.stage_transfer`가 예산 재검사를 하지 않아서, 미리 계산만 붙이면 승인 때 맞지 않는다. 붙일 때는 재검사와 함께 넣는다(코드의 `shortcut:` 주석).

## 생활비를 "금액 + 주기"로 (2026-11-12)

**배경** 생활비는 업종마다 "하루 금액" 하나만 받아 `남은 일수 × 하루 금액`을 남겨 뒀다. 실제로 써 보니 두 가지 문제가 있었다.
- 화면 안내가 "매일 **남겨 둘** 금액"이라, 사용자는 "남겨 둘 돈"이 아니라 "평소 **쓰는** 돈"을 적어야 하는 것 아니냐고 헷갈렸다.
- 외식·쇼핑·의료·주거통신·여가처럼 **가끔 쓰는 돈은 하루 금액으로 환산하기 어렵다**("외식은 주 2번 3만 원 정도").

**결정**
- 업종마다 `{amount, per, times}`로 받는다. `per`는 `day`(매일) · `week`(주 N회) · `month`(월 N회), `times`는 주 1~7번, 월 1~31번. 매일이면 `times`는 1.
- 남겨 둘 생활비(`essential_reserve`)
  - 매일 항목: 남은 일수(오늘 포함) × 금액 (지금과 같음)
  - 주·월 항목: **이번 주기 계획액 − 이번 주기에 그 업종에서 이미 쓴 돈** (0 아래로 안 감). 주 N회 계획액 = 금액 × N × 주기 일수 ÷ 7(올림), 월 N회 = 금액 × N
  - 매일 항목에 "이미 쓴 돈"을 빼지 않는 이유: 식비를 초과해도 남은 날의 밥값은 여전히 필요하다. 주·월 항목은 "이번 달 병원비 2만 원을 이미 썼으면 더 남길 필요가 없다"가 맞다.
- 완화 판정(PIN 필요)은 업종마다 **30일 기준 계획액**으로 비교한다. 매일 1만 원 → 월 1회 1만 원처럼 주기만 바꿔도 덜 남기게 되면 완화다.
- 저장은 기존 JSON 칸(`budget_profiles.essentials`) 그대로라 **마이그레이션이 없다**. 예전 값(하루 금액 정수)은 읽을 때 `매일`로 해석하고(`calc.essential`), API도 숫자 하나를 보내면 매일로 받는다.
- 화면 문구를 "생활비 (업종별로 쓰는 돈) — 평소에 쓰는 금액과 횟수"로 바꿨다. 처음 신청할 때 식사·교통·카페는 매일, 나머지는 월 1회로 시작한다.

**검토한 대안** 주·월 항목도 하루로 환산해 `남은 일수 × 하루 환산액`으로 남기기 — 계산은 단순하지만, 월 1회 항목은 월말에 거의 남기지 않고 이미 쓴 돈도 반영하지 못해 고르지 않았다.

**감수할 점** 주·월 항목은 지출 업종 분류(서버가 가맹점명으로 정함)에 기대므로, 분류가 틀리면 "이미 쓴 돈"이 틀린다. 주 N회는 주기 일수 ÷ 7로 나눠 계산해 실제 달력의 주 수와 조금 다를 수 있다.
