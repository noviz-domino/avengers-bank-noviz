# 0028. 모바일 웹 파일은 쓸 때마다 서버에 확인 (Cache-Control: no-cache)

- 상태: 채택
- 날짜: 2026-11-11
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0020](0020-mobile-app-real-api.md) `/app` 서빙, [ADR 0027](0027-compact-layout-chat-login.md) 로그인 화면

## 배경

- 모바일 웹(`frontend/`)은 빌드 없이 ES 모듈 그대로 `/app`에서 내보냅니다. 파일 이름이 버전마다 같습니다(`ui.mjs`, `login.mjs`).
- FastAPI의 `StaticFiles`는 `ETag`·`Last-Modified`만 붙이고 `Cache-Control`은 붙이지 않습니다. 이때 브라우저는 "마지막 수정 뒤 지난 시간의 일부" 동안 서버에 묻지 않고 캐시를 그대로 씁니다(휴리스틱 캐시).
- #46을 확인하다 실제로 흰 화면이 났습니다. 새 `login.mjs`는 `ui.mjs`의 `socialButton`을 가져오는데, 브라우저가 캐시의 옛 `ui.mjs`를 써서 `does not provide an export named 'socialButton'`로 앱 전체가 멈췄습니다. 배포 직후 사용자에게도 같은 일이 생길 수 있습니다.

## 결정

1. `/app` 아래 모든 응답에 `Cache-Control: no-cache`를 붙입니다(`main.py`의 `RevalidatedStaticFiles`).
2. `no-cache`는 "저장하지 마"가 아니라 "쓰기 전에 서버에 확인해"입니다. 안 바뀌었으면 서버가 `ETag`를 보고 **304(본문 없음)**로 끝내므로 다시 받는 비용이 거의 없습니다.

## 검토한 대안

| 대안 | 장점 | 단점 | 고르지 않은 이유 |
|---|---|---|---|
| 파일 이름에 버전 붙이기(`ui.mjs?v=46`) | 오래 캐시해도 안전 | import 문 전부에 버전을 달아야 하고 빠뜨리면 같은 문제 | 빌드 도구 없이 손으로 관리하기 어려움 |
| 빌드 도구(Vite 등)로 해시 파일 이름 | 업계 표준, 가장 효율적 | 빌드 단계·설정 추가 | 작은 앱에 비해 큼. 앱이 커지면 다시 검토 |
| Caddy에서 헤더 추가 | 앱 코드 변경 없음 | 로컬 개발(Caddy 없음)에서는 적용 안 됨 | 어디서 띄워도 같게 하려고 앱에서 처리 |
| `no-store` | 캐시 문제 원천 차단 | 매번 파일 전체를 다시 받음 | 304로 충분 |

## 결과

- 좋아지는 점: 배포하면 다음 요청부터 바로 새 파일을 씁니다. 옛 모듈과 새 모듈이 섞여 흰 화면이 되는 일이 없습니다. 테스트(`tests/test_static_cache.py`)가 헤더와 304를 지킵니다.
- 감수할 점: 화면을 열 때마다 파일 수만큼 확인 요청이 오갑니다(대부분 304). 파일이 많아지면 빌드 도구의 해시 이름 방식으로 옮깁니다.
- 팀 뼈대와의 차이: 팀 뼈대에는 모바일 웹 서빙이 없습니다.
