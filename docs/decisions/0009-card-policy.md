# 0009. 카드: 번호 형식, 가린 번호, 기본 한도, 정지는 바로·해제는 승인

- 상태: 채택
- 날짜: 2026-11-05
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0003](0003-db-redesign.md) 카드 한 테이블, [ADR 0004](0004-agent-integration.md) 승인, [ADR 0008](0008-account-opening-policy.md) 남의 것은 404

## 결정

1. **카드번호는 16자리 `9410 T PP NNNNNNNN C`**이다. `9410`은 데모용 발급사 번호(9는 어느 업종에도 배정되지 않음), T는 종류(1 신용, 2 체크), PP는 카드 상품 코드, N은 상품별 일련번호, C는 **Luhn 검증 숫자**다.
2. **응답에는 가린 번호만** 보낸다: `9410-20**-****-0017`(앞 6자리, 뒤 4자리). 전체 번호는 DB에만 있다.
3. 신용·체크카드는 **`cards` 한 테이블**이다(ADR 0003). 월 한도와 대금 출금일은 신용카드에만 있고 CHECK가 강제한다.
4. **기본 한도**: 체크 1일 100만, 신용 1일 100만·월 300만. 대금 출금일 기본 14일(1~28일). 한도를 올리는 것은 승인 기능과 함께 만든다.
5. **정지·분실 신고는 바로, 정지 해제는 PIN 승인**이다(ADR 0004 "안전해지는 쪽은 바로"). **분실은 되돌릴 수 없고** 재발급해야 한다.
6. 결제 계좌는 **카드 주인의 입출금 계좌**만 된다(ERD 규칙 10).
7. 카드 상품 목록(`GET /products/cards`)은 카드 도메인이 갖는다. `card_products` 테이블이 카드 도메인에 있어서다.

## 배경

- ERD의 "팀에서 정해야 할 것"에 카드번호 형식이 남아 있었다.
- 카드번호는 결제에 쓰이는 민감 정보라서, 응답·로그에 전체가 나가면 안 된다.
- 분실 신고를 승인 대기로 만들면 PIN을 입력하는 동안 카드가 살아 있다(PR #4 리뷰).

## 검토한 대안

### 번호 형식

| 대안 | 결과 |
|---|---|
| 실제 카드사 BIN(4·5로 시작) | 진짜 카드번호처럼 보여서 혼동될 수 있음. 버림 |
| 무작위 16자리 | 상품·종류를 번호로 알 수 없고 중복 검사가 필요. 버림 |
| **9410 + 종류 + 상품 + 일련번호 + Luhn** | **채택**. 계좌번호(ADR 0001)와 같은 방식이고, Luhn으로 한 자리 오타를 잡음 |

### 분실 후 다시 쓰기

| 대안 | 결과 |
|---|---|
| 분실도 정지처럼 해제 가능 | 잃어버린 카드가 누군가의 손에 있을 수 있음. 버림 |
| **분실은 영구, 재발급** | **채택**. 실제 카드사와 같음 |

## 결과

**좋아지는 점**
- 응답만 봐서는 카드번호를 알 수 없다. Agent·로그에도 가린 번호만 간다.
- 정지는 PIN 없이 바로 되므로 "카드 잃어버렸어, 정지해줘"가 즉시 처리된다.

**감수할 점**
- 같은 상품을 동시에 발급하면 번호가 겹쳐 `409 CARD_NUM_CONFLICT`가 날 수 있다(계좌번호와 같은 shortcut).
- 재발급 API는 아직 없다. 분실하면 새로 발급한다.

**팀 뼈대와의 차이**
- 팀 뼈대: 신용·체크 테이블 2개, `accumulated_amount` 저장, 카드번호 형식 미정 → 이 레포: 한 테이블, 누적 사용액은 계산(결제 PR), 위 형식
