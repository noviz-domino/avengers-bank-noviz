# 0037. 이름 선택지: 라우터가 내 계좌·카드 이름표에서 고르고 코드가 번호로 바꾼다

- 상태: 채택
- 날짜: 2026-11-27
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0034(빠른 길)](0034-agent-quick-lanes.md)·[0035(검색형 빠른 길)](0035-agent-search-quick-lane.md) 빠른 길, [ADR 0036(가벼운 라우터)](0036-router-light-model.md) 가벼운 라우터, [평가 기록](../evaluations/agent-latency/README.md)

## 배경

- 빠른 길 뒤에 남은 느린 질문은 "체크카드 한도 얼마 남았어?", "생활비 통장 상세 보여줘", "카드 사용내역 보여줘"였다(8~12초, LLM 4~5번).
- 호출 순서를 찍어 보니 4번은 "라우터 → 담당이 목록 도구로 번호 찾기 → 담당이 상세 도구 고르기 → 담당이 답 쓰기"였다. 사람은 이름으로 말하고 도구는 번호(`card_id`·`account_id`)를 받아서, 번호를 찾느라 LLM이 한 번 더 들었다.
- 이전 프로젝트(노비즈 뱅크)는 사용자의 실제 계좌·카드 이름을 스키마의 선택지(Literal)로 줘서 LLM 한 번으로 대상을 정했다. 그 장치를 가져온다.

## 결정

1. **라우터 앞에서 코드가 내 계좌·카드 목록을 부른다** (`agent/quick.py`의 `load_targets`, LLM 없음, 두 목록을 동시에). 실패하면 선택지 없이 지금처럼 돈다.
2. **이름표를 라우터 양식의 선택지로 준다** (`graph.py`의 `plan_schema`). 계좌는 "생활비 (110-101-000001)", 카드는 "캡아메리카 체크카드 •••• 0033 (사용 중)". 선택지에 없는 계좌·카드는 양식이 거절해서 라우터가 지어낼 수 없다. 고른 이름표는 코드가 실제 계좌·카드로 바꾼다(`resolve`).
3. **빠른 길 셋을 더한다** (도구는 번호를 알고 바로 부른다).
   - `card_limit`: 카드 한도. 카드를 말하지 않으면 사용 중인 카드 전부. 남은 금액은 서버 숫자로 코드가 뺀다
   - `card_txs`: 카드 최근 사용내역. 카드 이름·종류·끝자리를 콕 집어 말했을 때만 그 카드, 그냥 "카드"면 모든 카드를 합쳐 최근 순
   - `account_detail`: 계좌 상세(잔액·이체 한도·금리·만기). 계좌를 분명히 골랐을 때만, 아니면 담당 Agent가 되묻는다
4. **라우터 표시를 코드가 한 번 더 거른다** (`lane_allowed`). 금액이 있는 예산 질문("30만 원짜리 사도 돼?")은 남은 예산 요약 빠른 길을 쓰지 않고 예산 담당이 `check_budget`으로 답한다. 이 장치를 넣은 이유는 아래 "가벼운 라우터의 흔들림"이다.
5. **진행 표시에 목록 조회를 넣지 않는다**: 라우터 앞의 목록 조회는 사용자에게 보여 줄 단계가 아니다(`stream.py`).

## 가벼운 라우터의 흔들림 (ADR 0036(가벼운 라우터)의 후속)

- 최종 측정 중 "30만 원짜리 사도 돼?"가 LLM 1번으로 끝난 것을 보고 같은 질문을 반복해 물었다. 가벼운 라우터(`gemini-3.5-flash-lite`)는 **8번 중 4번** 남은 예산 빠른 길로 표시했다. 그러면 "사도 되는지" 대신 일반 예산 요약이 나간다. 담당은 맞아서 라우팅 점수(21/21)로는 보이지 않았다.
- 이 모델은 temperature 설정을 무시한다(실행 경고: "uses fixed sampling defaults"). ADR 0036(가벼운 라우터)의 칸 채우기 시험은 질문당 한 번이라 이런 흔들림을 잡지 못했다.
- 평가 질문 21개와 추가 3개를 3번씩 물으니 24개 중 3개가 흔들렸다: "30만 원짜리 사도 돼?"(금액 장치로 막음), "목표 저축 잘 지키고 있어?"(요약이 나가도 목표 저축 줄이 들어 있어 주제는 맞음), "예산 관리는 어떻게 신청해?"(맞는 담당 둘 사이). 원본: [13](../evaluations/agent-latency/2026-11-27_13-router-repeat-probe.txt), 스크립트: [`router_repeat_probe.py`](../evaluations/agent-latency/router_repeat_probe.py)
- 그래서 **틀린 표시가 틀린 답이 되는 길은 코드로 막는다**는 원칙을 더했다. 표시가 넘쳐도 결과가 넓어지기만 하는 길(잔액 전체, 사용 중인 카드 전부)은 그대로 둔다.

## 검토한 대안

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 담당 Agent에 목록을 미리 넣기 | 4번 → 3번 | 이름 선택지는 4번 → 1번. 담당 LLM 두 번이 그대로 남음 |
| 라우터가 번호(id)를 직접 쓰게 | 칸이 단순 | 모델이 없는 번호를 지어낼 수 있음. 이름표 선택지는 양식이 막음 |
| 라우터 흔들림을 프롬프트로만 고치기 | 코드 변경 없음 | 모델이 temperature를 무시해서 프롬프트로는 확률만 낮춤. 틀린 답이 되는 길은 코드가 막는 편이 확실 |
| 라우터를 원래 모델로 되돌리기 | 흔들림이 적을 수 있음 | 라우터 한 번이 2.5초로 돌아감. 장치 하나로 위험한 길만 막는 편이 이득이 큼 |

## 결과

- 좋아지는 점: 21개 질문의 p50이 1.1초, 흔한 조회는 거의 모두 1초 안팎이다. 이름표 선택지라 라우터가 없는 계좌·카드를 고를 수 없다.
- 감수할 점: 턴마다 목록 두 개를 부른다(REST 수십 ms, 인사에도). 가벼운 라우터는 드물게 다르게 표시하므로 새 빠른 길을 더할 때마다 반복 시험(`router_repeat_probe.py`)으로 흔들림을 보고 틀린 답이 되는 길은 `lane_allowed`에 막는다.
- 남은 느린 질문: 상품 목록·약관(RAG 답변 호출), 금액이 있는 예산 질문, "이체 한도가 얼마야?"처럼 계좌를 말하지 않은 상세 질문. 모두 담당 Agent나 RAG가 판단해야 하는 일이다.
