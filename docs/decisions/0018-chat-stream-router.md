# 0018. 채팅 스트리밍(진행 상태 + 답 글자)과 "감독관" → "라우터" 이름 바로잡기

- 상태: 채택
- 날짜: 2026-11-06
- 관련 PR: (이 문서를 추가하는 PR)
- 관련: [ADR 0015](0015-agent-chat.md) Agent, [ADR 0016](0016-agent-latency-tracing.md) 턴마다 한 번 계획

## 결정

1. **`POST /chat/stream`**을 더한다(SSE). 기존 `POST /chat`은 그대로 둔다(사용자 결정: 진행 상태 + 스트리밍).
   - `status`: 담당 고르기 → 담당 결정("카드 → 계좌 순서로 확인할게요") → 담당 시작 → 도구 실행("잔액을 조회하고 있어요")
   - `token`: 담당 AI가 쓰는 답의 글자 조각(`agent`로 담당 구분). **복합 요청은 먼저 끝난 담당의 답부터** 보내고, 다음 담당 답 앞에 빈 줄
   - `done`: 대화방 id, 최종 답(`reply`), 일한 담당
   - `error`: 중간 실패(HTTP는 이미 200이라 이벤트로)
2. LangGraph `astream_events`(v2)를 화면용 이벤트로 바꾼다(`agent/stream.py`). **라우터의 계획(JSON)과 담당의 도구 결정은 token으로 내보내지 않는다.** 글자 단위로 못 주는 모델은 끝날 때 한 번에 보낸다.
3. 같은 대화방 잠금은 **스트림을 열기 전에** 잡는다. 처리 중이면 스트림 대신 `409 CHAT_BUSY`. 턴은 별도 작업으로 끝까지 돌고, 스트림은 큐에 쌓인 이벤트만 읽는다. 연결이 끊겨도 대화가 저장된다. 잠금은 턴 작업이 끝날 때 푼다.
4. **"감독관(supervisor)"을 "라우터(router)"로 부른다.** ADR 0016 이후 이 노드는 턴 처음에 한 번 담당 순서를 정하고 다시 관여하지 않는다. 담당이 끝날 때마다 제어가 돌아오는 감독관 패턴이 아니다. 코드(노드 `router`, 프롬프트 `ROUTER`)와 지금 구조를 설명하는 문서를 고친다. 이전 ADR은 그때의 기록이라 그대로 둔다.
5. 담당들의 답을 **AI가 다시 종합하지 않는다**(오케스트레이터-워커 아님). 담당이 사용자에게 할 말을 직접 쓰고, 코드가 순서대로 이어 붙인다.
6. 상품 담당은 RAG 답과 근거에 없는 내용을 덧붙이지 않는다(실제 점검에서 "신용도 영향"을 덧붙인 일이 있어 규칙을 더함).

## 측정 (2026-11-06, 실제 gemini-3.8-flash, 로컬 Docker)

| 질문 | 첫 진행 표시 | 담당 결정 | 첫 글자 | 끝 |
|---|---|---|---|---|
| 내 계좌 잔액 알려줘 | 0.3초 | 3.0초 | 7.3초 | 8.4초 |
| 카드 한도랑 내 잔액 (복합) | 0.0~0.3초 | 2.7~3.0초 | 9.8~10.4초 | 17초 |
| 카드 대금 못 내면? (RAG) | 0.0초 | 3.9~4.7초 | 13~14초 | 13.6~14.7초 |

끝나는 시간은 `/chat`과 같고, 처음부터 2~3초마다 진행 상태가 바뀐다.

## 배경

- 응답 시간 p50 8초, p95 17초(ADR 0016)인데 화면이 그동안 멈춰 있으면 고장 난 것처럼 보인다.
- 스트리밍만으로는 첫 글자가 5~7초쯤 나온다. 담당 고르기와 도구 결정은 사용자에게 보낼 글이 없기 때문이다. 그래서 진행 상태를 같이 보낸다.
- 사용자가 "이건 라우터 아니냐"고 짚었다. 맞다: 감독관을 턴마다 한 번으로 줄이면서(ADR 0016) 성질이 라우터가 됐다.

## 검토한 대안

| 주제 | 대안 | 결과 |
|---|---|---|
| 전송 | WebSocket | 양방향이 필요 없고, 끊김·재연결 처리가 늘어남. 버림 |
| 전송 | **SSE (HTTP 응답을 흘려보냄)** | **채택**. 보통 HTTP라 인증·요청 한도·프록시가 그대로 |
| 이벤트 | 답 글자만 | 첫 글자까지 5~7초 동안 아무것도 안 보임. 버림 |
| 복합 요청 | 종합 노드(AI가 답을 다시 씀) | AI 호출 한 번 더(2~3초), 모든 담당이 끝나야 첫 글자. 버림 |
| 이름 | 감독관 그대로 | 실제 동작과 다른 이름이라 설명할 때 틀린 말을 하게 됨. 버림 |

## 결과

**좋아지는 점**
- 사용자는 0초부터 "무엇을 하는지"를 보고, 답은 만들어지는 대로 본다.
- 복합 요청은 첫 담당의 답이 끝나는 대로 보인다.
- 구조의 이름이 실제 동작과 같다.

**감수할 점**
- 도구 호출 전의 “확인해 볼게요” 같은 서문은 `token`으로 나갈 수 있고 `done.reply`에서는 빠진다. 화면은 `token`을 미리보기로 표시하고, `done`을 받으면 표시한 텍스트를 `done.reply`로 바꿔 끼운다.
- 인사처럼 라우터가 혼자 답하면 `token` 없이 `done.reply`로만 답이 온다.
- 실제로 빨라지지는 않는다. 끝나는 시간은 그대로다.
- 약관 질문은 상품 담당 안에서 RAG가 Gemini를 한 번 더 부르고 그 답을 다시 옮겨 써서, 첫 글자가 13초쯤이다. RAG 답을 바로 흘려보내거나 상품 담당을 거치지 않게 하면 줄어든다(다음 후보).
- 두 답을 엮은 판단("한도는 남았고 잔액도 넉넉하니 써도 돼요")은 하지 못한다.
- 중간 실패는 HTTP 상태가 아니라 `error` 이벤트로만 알 수 있다.
