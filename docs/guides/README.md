# 코드 가이드 (면접 대비)

> **코드를 처음부터 다 읽지 않아도, 기능마다 "요청이 어디로 흘러가고, 왜 그렇게 만들었고, 면접에서 무엇을 물을지"를 알 수 있게 정리한 문서입니다.**

- 설계 결정의 원문은 [ADR](../decisions/README.md), 테이블은 [ERD](../ERD.md), API 목록은 [API_ENDPOINTS](../API_ENDPOINTS.md)에 있습니다. 이 가이드는 그 문서들을 **코드와 이어서** 설명합니다.
- 기능 PR마다 그 기능의 가이드를 같은 PR에서 갱신합니다.

## 면접에서 한 문장으로 말한다면

> "은행 백엔드에 AI Agent를 붙이려고, **로그인 토큰만으로는 돈이 움직이지 않고 거래 PIN 승인이 있어야 실행되도록** 서버에서 강제했습니다. 돈이 바뀌는 코드는 실행 함수 하나로 모아서 잠금 순서·재검사·장부 기록을 한 곳에서 지킵니다."

(Agent·MCP 연결은 아직 만들기 전입니다. 지금 서버가 보장하는 것은 "PIN을 아는 사람이 승인해야 실행"이고, Agent 도구에서 승인 API를 빼는 것은 Agent PR에서 합니다: ADR 0004)

## 자주 나오는 단어

| 단어 | 이 프로젝트에서 |
|---|---|
| 트랜잭션 | 여러 DB 변경을 "전부 되거나 전부 안 되게" 묶은 것. `async with db.begin():` 블록 하나 |
| 행 잠금 (`FOR UPDATE`) | 이 행을 내가 다 쓸 때까지 다른 요청이 못 바꾸게 함. 잔액을 바꿀 때 씀 |
| 조건부 UPDATE | `UPDATE … WHERE 상태가 아직 대기 중`. 동시에 두 번 와도 한 번만 바뀜. 로그인 시도 예약, 승인, 토큰 교체에 씀 |
| 멱등키 (idempotency key) | 같은 요청을 두 번 보내도 한 번만 처리되게 요청에 붙이는 번호 |
| 장부 (ledger) | `account_transactions`. 모든 돈의 움직임이 +/− 금액으로 쌓임 |
| 승인 대기 (`pending_actions`) | "이런 일을 하려고 한다"를 저장해 두고 사람이 PIN으로 승인하면 실행 |
| CHECK 제약 | DB가 직접 막는 규칙. 예: 잔액 0 이상, 나가는 거래는 금액이 음수 |
