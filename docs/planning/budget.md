# 예산 관리

> **월급날까지 "자유롭게 쓸 수 있는 돈"을 계속 계산하고, 그 돈을 넘는 결제는 사용자가 직접 확인해야만 실행한다.**

이 프로젝트만의 차별 기능입니다. 결정 이유: [ADR 0002](../decisions/0002-budget-guard-and-scope.md)

## 한눈에 보기

- **신청한 사람만** 씁니다. 처음 한 번 수입·고정 지출·예상 생활비·목표를 입력합니다.
- 중심 숫자는 하나, **자유 사용 가능액**입니다. 화면, 결제 검사, AI 조언이 모두 이 숫자를 씁니다.
- 결제(체크카드·신용카드·계좌 이체)가 이 숫자를 넘으면 **멈추고 이유를 보여준 뒤, 사용자가 화면에서 직접 확인해야 진행**합니다. **AI는 이 확인을 대신할 수 없습니다.**
- 둘째 달부터는 **실제 거래내역을 분석**해서 예산 조정을 제안합니다. 바꾸는 건 항상 사용자 승인 후입니다.
- **계산은 코드, 설명과 제안은 AI**가 합니다. AI는 숫자를 만들지 않습니다.

## 중심 숫자: 자유 사용 가능액

```
자유 사용 가능액 = 남은 돈
                - 아직 안 낸 고정 지출          (월세, 공과금 …)
                - 남은 기간의 필수 생활비        (식사·교통 등 매일 쓰는 필수 지출)
                - 묶어 둔 목표 저축             (주기 끝에 적금으로 이체할 돈)
```

- **남은 돈** = 이번 주기 수입 - 이번 주기에 쓴 돈 (신용카드 포함, 아래 "돈의 종류" 기준)
- 화면에는 **두 줄**로 보여줍니다. 저축을 빼기 전과 후가 달라서, 실제로 생활비가 모자라는지 저축까지 지키려면 모자라는지를 구분합니다.
  ```
  생활비만 보면       -18.7만   ← 저축을 풀어도 모자람
  저축까지 지키면     -43.7만   ← 자유 사용 가능액
  ```

## 지출의 세 종류

| 종류 | 예 | 계산 방식 |
|---|---|---|
| **고정 지출** | 월세, 통신비, 보험, 구독, **대출 상환** | 매달 거의 같은 금액. 목록으로 등록. 나가는 날이 지나면 "낸 것"으로 처리 |
| **필수 생활비** | 식사, 교통 | 매일 조금씩, 금액이 들쭉날쭉. **남은 일수만큼 미리 떼어 둠** |
| **선택 지출** | 외식·술자리·회식, 쇼핑, 여가 | 자유 사용 가능액 안에서만 |

- 카테고리마다 **필수/선택**을 사용자가 정합니다. 분석이 "매달 13일에 13,500원"처럼 반복 결제를 찾으면 **고정 지출로 추천**하고, 사용자가 승인하면 등록합니다.
- **식사와 외식·술자리는 다른 카테고리**입니다. 회식이 필수 생활비에 섞이지 않게 합니다.
- **의료·약국처럼 가끔 쓰는 필수 지출은 미리 떼어 두지 않고**, 결제할 때 항상 통과시킵니다(아래 "결제 검사").
- 대출을 받으면 **상환액이 고정 지출에 자동으로 들어갑니다.**

## 규칙

| # | 규칙 | 이유 |
|---|---|---|
| 1 | **주기는 등록한 월급날 날짜에 시작해서 다음 월급날 전날에 끝남.** 수입은 등록 금액으로 예상하고, 실제 월급이 들어오면 그 금액으로 바꾸고 알림 | 달력 기준이면 월급 전후로 돈이 몰리거나 모자람. 월급이 하루 늦어도 주기는 흔들리지 않음 |
| 2 | **모든 지출은 쓴 주기에서 한 번만 차감.** 신용카드도 쓴 순간 차감하고 "청구 예정"으로 묶음 | 같은 돈을 두 번 빼지 않기 위해. 카드 결제일이 월급날 전이든 후든 똑같이 동작 |
| 3 | **돈의 종류별로 셈** (아래 표). 카드 대금 출금과 내 계좌끼리의 이동은 "쓴 돈"이 아님 | 규칙 2를 거래내역에서 구현하려면 출금마다 성격이 구분돼야 함 |
| 4 | **필수 생활비 = 카테고리별로 (최근 주기들의 주기 합계 중앙값) × (남은 일수 ÷ 주기 일수)**, 첫 주기는 신청 때 입력한 값 | 하루 단위 중앙값은 지출이 없는 날이 많으면 0이 됨. 주기 합계로 보면 주말·평일 차이도 흡수됨. 평균은 튀는 달에 크게 부풀어서 중앙값 |
| 5 | **목표 저축은 주기 시작에 묶어 두고, 주기 마지막 날 적금으로 이체.** 주기 중 여유가 없으면 사용자가 묶음을 풀 수 있음 _(추천안, 결정 대기)_ | 월급날 바로 이체하면 주기 중에 부족할 때 되돌릴 수 없음. 신용카드처럼 "묶어 두기"로 통일 |
| 6 | **저축액은 주기마다 다시 계산**: 남은 목표 금액 ÷ 남은 주기 수 | 못 모은 달은 다음 주기들에 나눠 반영 |
| 7 | **결제 검사 대상은 체크카드, 신용카드, 계좌 이체 전부** _(추천안, 결정 대기)_ | 충동구매는 송금으로도 함 |
| 8 | **환불·취소**: 같은 주기면 쓴 돈에서 빼고, 다음 주기에 들어오면 그 주기의 수입처럼 더함 | 원래 주기는 이미 끝나서 되돌릴 수 없음 |
| 9 | **주기 끝에 남은 돈은 다음 주기로 이월** _(추천안, 결정 대기)_. 주기 시작 때 "목표 저축에 보탤까요?"를 물어봄 | 아껴 쓴 돈이 사라지면 아낄 이유가 없음 |
| 10 | **예산 변경은 제안만, 반영은 사용자 승인 후** | 분석 결과로 예산이 마음대로 바뀌면 안 됨 |

### 돈의 종류 (규칙 3)

| 거래 | 예산에서 | 장부 `tx_type` ([ERD](../ERD.md)) |
|---|---|---|
| 체크카드 결제, 송금, 고정 지출 출금 | **쓴 돈** | `CARD_PAYMENT`, `TRANSFER_OUT`, `WITHDRAW` |
| 신용카드 결제 | **쓴 돈** (쓴 순간) | 장부가 아니라 `card_transactions` |
| 신용카드 대금 출금 | 셈하지 않음 (이미 쓴 순간 셈) | `CARD_BILL` |
| 목표 저축 적금 이체 | 셈하지 않음 (묶어 둔 돈이 옮겨감) | `GOAL_SAVING_OUT` / `GOAL_SAVING_IN` |
| 내 계좌끼리 이동 | 셈하지 않음 | `INTERNAL_OUT` / `INTERNAL_IN` |
| 대출 상환 | 고정 지출 | `LOAN_REPAY` |
| 월급, 이자, 환불 | 수입 | `DEPOSIT`, `TRANSFER_IN`, `INTEREST`, `REFUND` |

### 신청 첫 주기 (예외)

신청 **전에** 쓴 신용카드 금액은 어느 주기에서도 차감되지 않았습니다. 그래서 신청할 때 **"청구 예정인 카드값"을 첫 주기의 고정 지출로** 넣습니다. 카드 사용내역에서 아직 청구되지 않은 금액을 자동으로 채우고, 사용자가 확인합니다.

## 예시

같은 사람의 예시입니다.

| 가정 | 값 |
|---|---|
| 월급 | 300만 원, 주기 30일 |
| 고정 지출 150만 | 월세 60, 공과금 15, 통신 10, 보험·구독 15, 대출 상환 50 |
| 필수 생활비 | 식사 하루 1.5만, 교통 하루 0.4만 (= 하루 1.9만, 30일 57만) |
| 목표 | 휴대폰 150만, 6개월 → 주기마다 25만 |

### 평소: 월급날

```
남은 돈 (이번 주기 수입)          300만
  아직 안 낸 고정 지출             -150만
  필수 생활비 1.9만 × 30일          -57만
  묶어 둔 목표 저축                 -25만
──────────────────────────────────
자유 사용 가능액                    68만
```

충동구매 30만 원 → 68만 이내라 **통과**. 결제 후 자유 사용 가능액 38만.

### 부족: 7일 만에 200만 원을 썼을 때

7일 동안 쓴 200만 = 이미 낸 고정 지출 75만(통신 10, 보험·구독 15, 대출 상환 50) + 필수 생활비 13.3만(1.9만 × 7일) + 선택 지출 111.7만

```
남은 돈 (300 - 200)                           100만
  아직 안 낸 고정 지출 (월세 60, 공과금 15)        -75만
  필수 생활비 1.9만 × 23일                       -43.7만
──────────────────────────────────────────
생활비만 보면                                 -18.7만
  묶어 둔 목표 저축                              -25만
──────────────────────────────────────────
자유 사용 가능액 (저축까지 지키면)               -43.7만  ⚠️
```

사용자에게 보여주는 것 (주기당 한 번, 상황이 더 나빠지면 다시):

```
⚠️ 이번 주기에는 여유가 없어요.
   생활비만으로도 월급날 전에 18.7만 원이 모자라고, 휴대폰 저축까지 하려면 43.7만 원이 모자라요.

  ① 이번 주기 휴대폰 저축 풀기            → 부족분 18.7만 (목표일 1개월 늦어짐)
  ② 식사를 하루 1.5만 → 1만으로 줄이기     → 부족분 32.2만 (0.5만 × 23일 = 11.5만 절약)
  ③ 둘 다                                → 부족분 7.2만

  허리띠 모드: 월세·공과금을 내고 나면 하루 1.1만 원으로 지내야 해요. ((100 - 75) ÷ 23일)
```

어떤 걸 고를지는 **사용자가 정합니다**. 고른 내용은 이번 주기 계획에 반영됩니다.

## 결제 검사

| 상황 | 결과 | 응답 |
|---|---|---|
| 결제 금액 ≤ 자유 사용 가능액 | **통과** | 그대로 결제 |
| 결제 금액 > 자유 사용 가능액 | **확인 요청** | `409 BUDGET_CONFIRMATION_REQUIRED` + 승인 대기 작업(`pending_actions`) + 영향 설명 ("월세 낼 돈이 부족해져요", "휴대폰 목표가 1개월 늦어져요") |
| 사용자가 화면에서 **사유를 적고 확인** | **다시 검사 후 결제** | 사유와 결정을 기록 |
| 필수 업종 (의료·약국) | **항상 통과** | 자유 사용 가능액이 마이너스여도 결제. 기록만 남김 |
| 확인 화면에서 **"긴급"** 사유 선택 (경조사, 급한 수리 등) | **통과** | 업종으로 알 수 없는 긴급 상황. 기록만 남김 |
| 예산 관리를 신청하지 않은 사람 | 검사 안 함 | 일반 결제 |

### 확인은 사람만 할 수 있다

- 확인 요청 때 **승인 대기 작업**(`pending_actions`, 10분 유효)을 만듭니다. 다른 돈 이동과 같은 승인 구조입니다([ADR 0004](../decisions/0004-agent-integration.md)).
- 승인은 **은행 화면에서 거래 PIN 또는 패스키**로만 합니다([ADR 0005](../decisions/0005-auth.md)). 자연어 Agent의 도구에는 **승인 API가 없습니다.** Agent는 "승인 화면으로 가기" 링크만 줄 수 있습니다.
- 사유는 **사용자가 승인 화면에서 직접** 입력합니다.
- 그래서 Agent가 사용자 토큰을 갖고 있어도 예산 초과 결제를 스스로 진행할 수 없습니다.

### 동시성과 중복

- 결제 처리 순서: **① 사용자의 현재 주기 행(`budget_cycles`) 잠금 → ② 출금 계좌 행 잠금(체크카드·이체) → ③ 예산 검사 → ④ 잔액 검사 → ⑤ 기록.** 항상 같은 순서로 잠가서 교착(deadlock)을 막습니다.
- 주기 행을 잠그기 때문에 **신용카드 결제와 이체가 동시에 와도** 하나씩 처리됩니다.
- 확인 후 다시 오는 요청은 그사이 상황이 바뀌었을 수 있어서 **처음부터 다시 검사**합니다. 더 나빠졌으면 새 확인 요청을 돌려줍니다.
- **멱등키는 처음 결제 요청의 키**를 그대로 씁니다. 확인 요청은 승인 대기 작업의 id로 처음 요청과 연결됩니다. 같은 확인이 두 번 와도 결제는 한 번만 됩니다.

## 이용 단계

| 단계 | 언제 | 무엇을 |
|---|---|---|
| ① 신청 | 처음 한 번 | 월 수입, 월급날, 고정 지출(이름·금액·나가는 날), **카테고리별 예상 생활비**(식사·교통 하루 얼마), 필수 카테고리, 청구 예정 카드값. AI가 대화로 받고 표로 정리 → **사용자 확인 후 저장** |
| ② 목표 등록 | 원할 때 | "6개월 뒤 휴대폰". 가격은 AI가 추정 → **사용자가 확정** → 주기마다 저축액 계산 |
| ③ 주기 시작 | 매 월급날 | 지난 주기 남은 돈 이월 처리, 목표 저축 **묶어 두기**, 이번 주기 계획 생성 |
| ④ 결제할 때 | 매 결제 | 결제 검사 (위 표) |
| ⑤ 여유 없을 때 | 자유 사용 가능액 < 0 | 경고 + 선택지 + 허리띠 모드 |
| ⑥ 주기 끝 | 다음 월급날 전날 | 묶어 둔 저축을 **적금으로 이체**, 소비 패턴 분석, 다음 주기 조정 제안 |

## 소비 패턴 분석 (둘째 달부터)

### 분석 기간

| 쌓인 데이터 | 기준 |
|---|---|
| 1주기 미만 | 신청 때 입력한 값 |
| 1~2주기 | 지난 주기 + "데이터가 적어 정확도 낮음" 표시 |
| 3~5주기 | 최근 3주기 |
| 6주기 이상 | 최근 3주기와 6주기 비교 (추세) |

### 보여주는 숫자

| 숫자 | 쓰는 곳 | 예 |
|---|---|---|
| **중앙값** (주기 합계) | 필수 생활비 계산 | 식사 한 주기 45만 → 하루 1.5만 |
| **보통 범위** (하루 지출의 하위 25%~상위 25%) | 화면 표시 | "식사는 보통 하루 0.9만~1.4만 원" |
| **가장 자주 쓰는 금액대** (1천 원 단위로 묶은 최빈값) | 화면 표시 | "식사는 8천~9천 원대가 가장 많아요" |

최빈값은 금액이 거의 같은 값으로 반복되지 않아서(8,500원, 9,200원 …) 구간으로 묶어야 하고, 묶는 폭에 따라 결과가 달라집니다. 그래서 계산에는 쓰지 않고 표시에만 씁니다.

### 찾아내는 것

| 분석 | 조언 예시 |
|---|---|
| 입력값과 실제의 차이 | "교통비를 하루 0.4만 원으로 적으셨는데 최근 3주기 중앙값은 0.5만 원이에요. 예산을 고칠까요?" |
| 카테고리별 추세 | "외식·술자리가 3주기 연속 늘고 있어요 (12만 → 15만 → 19만)" |
| 평소보다 튀는 주기 | "이번 주기 쇼핑이 평소의 2배예요" |
| 숨은 고정 지출 | "매달 13일에 13,500원이 나가요. 고정 지출에 추가할까요?" (같은 가맹점, 비슷한 금액, 매달 반복) |
| 목표 달성 예측 | "지금 추세면 휴대폰 목표가 1개월 늦어져요" |
| 다음 주기 예측 | 고정 지출 + 필수 생활비 + 선택 지출 중앙값 |

## AI가 하는 일과 하지 않는 일

| AI가 한다 | AI가 하지 않는다 |
|---|---|
| 신청할 때 대화로 수입·지출 받기 → 표로 정리 | 저장 (사용자 확인 후 코드가 저장) |
| 목표 상품 가격 추정 | 가격 확정 (사용자가 확정) |
| 분석 결과와 결제 영향을 **사람 말로 설명** | 중앙값·추세·남은 금액 **계산** (코드가 계산해서 넘겨줌) |
| 조정안 제안 | 예산 변경 (사용자 승인 후 코드가 변경) |
| 예산 초과 결제에서 "확인 화면" 링크 안내 | **예산 초과 결제 확인** (사용자가 화면에서 직접) |
| 가맹점 카테고리 분류 (규칙으로 안 되는 것만) | — (사용자가 고칠 수 있음) |

## 필요한 데이터

[ERD의 "예정"](../ERD.md#예정) 표에 있습니다: `budget_profiles`, `fixed_expenses`, `savings_goals`, `budget_cycles`(결제 검사 때 잠그는 행), `budget_decisions`, `categories`, `product_preferential_rates`. 예산 기능을 구현하는 PR에서 컬럼을 확정하고 ERD 본문에 옮깁니다. 장부의 거래 종류(`tx_type`)는 이미 ERD에 있습니다.

## 결정 대기

추천안으로 기획했고, 구현 전에 다시 확인합니다.

| 항목 | 추천안 | 다른 안 |
|---|---|---|
| 예산 초과 시 방식 | **확인 모드 하나로 시작** | 알림 모드(결제는 되고 안내만), 잠금 모드(24시간 대기) 추가 |
| 목표 저축 | **주기 시작에 묶고, 주기 끝에 적금으로 실제 이체** | 월급날 바로 이체, 묶어 두기만(가상) |
| 검사 대상 | **체크카드, 신용카드, 계좌 이체** | 카드만 |
| 남은 돈 | **다음 주기로 이월** | 매 주기 0에서 시작 |
| 데모 데이터 | **6개월치 가상 거래 seed** | 없음 (데모에서 분석 화면이 비어 있음) |
