# 구현 범위

> **돈 처리·보안·예산 관리·자연어 Agent를 깊게 만들고, 대출을 포함한 나머지는 가볍게 만든다.**

포트폴리오로 쓰는 개인 구현 레포의 범위입니다. 팀 기획(기능 41개)에서 골랐고, 결정 이유는 [ADR 0002](../decisions/0002-budget-guard-and-scope.md)에 있습니다.

## 한눈에 보기

| 깊게 🟢 | 가볍게 🟡 | 빼거나 자리만 ⚪ |
|---|---|---|
| 이체 (동시성·멱등) | 카드 (체크·신용 결제, 정지) | 영업점 우대 (자리만) |
| 상품·금리 (가입 조건·우대·특판) | **대출** (신청·자동 심사·실행·상환) | SNS·휴대폰 인증 |
| 보안·인증 | 거래내역 조회·검색 | 자동이체 일반 기능, 지출 그래프 |
| **예산 관리** | 모바일 웹 화면 | 대출 서류·연체·중도상환 |
| 자연어 Agent + RAG | 알림 (저장·조회만) | |
| 배포·CI | | |

## 이 프로젝트가 보여줄 것

> **이전 포트폴리오의 Agent는 JSON 장부를 고쳤다. 이번에는 인증·트랜잭션·동시성이 있는 실제 은행 백엔드를, Agent가 사용자 권한으로 안전하게 호출하고, 결제 순간에 예산을 지킨다.**

| 이전 레포 | 이번에 더하는 것 |
|---|---|
| [langgraph-financial-agent](https://github.com/noviz-domino/langgraph-financial-agent): 승인 후 실행하는 은행 Agent, JSON 장부 | 실제 DB·인증·동시성 위에서 같은 승인 패턴 |
| financial-rag-agent-solo: 금융 문서 RAG와 평가 | pgvector로 옮겨 상품·약관 질문에 사용 (과제 요구: 지난 미니 프로젝트의 RAG) |
| — | **예산 관리**: 결제 순간에 현금 흐름을 예측해서 개입 |

## 영역별 범위

### 🟢 깊게

| 영역 | 포함 | 보여주는 것 |
|---|---|---|
| **이체** | 잔액·1회·1일 한도 검사, **행 잠금**(동시 이체에도 잔액이 꼬이지 않음), **멱등키**(같은 요청 두 번에도 한 번만 이체), 거래내역 2건 | 돈 처리의 정확성 |
| **상품·금리** | 가입 조건(기간·금액·조건 설명), 기본금리 + **조건형 우대금리**, **특판 기간**, 계좌에 가입 당시 금리 확정 | 은행 도메인 이해 |
| **보안·인증** | 로그인 5회 실패 잠금, refresh token과 로그아웃 시 무효화, 모든 API **소유권 검사(남의 것은 404)**, 돈 이동 **감사 기록** | 인증·인가 |
| **예산 관리** | [budget.md](budget.md) 전체 | 이 프로젝트만의 기능 |
| **자연어 Agent** | 감독관 + 도메인 Agent 5개(계좌·카드·대출·예산·상품, [ADR 0006](../decisions/0006-agent-orchestration.md)), 되묻기, 대화 맥락, **돈이 움직이면 사용자 승인 후 실행**, Agent도 **사용자 토큰 권한으로만** 호출. 단 **예산 초과 결제 확인처럼 사람이 직접 해야 하는 단계는 Agent 도구에서 뺌** ([budget.md](budget.md) "확인은 사람만 할 수 있다") | LLM을 서비스에 안전하게 붙이기 |
| **RAG** | 상품 설명·우대 조건·약관을 pgvector에 저장, 근거와 함께 답변, 작은 골든셋으로 Hit@k·MRR 측정 | 과제 요구 + 평가 습관 |
| **배포·CI** | PR마다 테스트(GitHub Actions), 동시성 테스트는 PostgreSQL로, EC2 + Docker + Nginx + HTTPS, 데모 계정 | 바로 써 볼 수 있는 결과물 |

### 🟡 가볍게

| 영역 | 포함 | 빼는 것 |
|---|---|---|
| 카드 | 발급, 체크·신용 결제(예산 검사 포함), 정지·잠금, 사용내역 | 신용카드 청구서·이용 기간 계산 |
| 대출 (16개 중 9개) | 상품 조회(금리·한도·조건), 한도 조회(소득 기반 단순 규칙), 신청 → **규칙 기반 자동 심사**(승인·거절과 사유), 실행(입출금 계좌로 입금), 대출 계좌 조회(잔액·다음 납입일), 이자 계산과 상환 일정(원리금균등 하나), 상환(계좌 출금). 상환액은 예산 관리의 **고정 지출에 자동 등록** | 상품 비교, 서류 제출, 상환 방식 비교, 중도 상환, 연체 관리, 만기 관리, 대출 알림 (7개) |
| 거래내역 | 조회, 기간·금액·키워드 검색, 카테고리 | 지출 그래프 |
| 화면 | 모바일 웹: 로그인, 계좌, 이체, 카드, 예산, 채팅 | 실제 은행 수준의 디자인 |
| 알림 | 테이블 저장과 목록 조회 | 실시간 푸시 |
| 예·적금 | 가입, 납입, 이자 계산, 만기 조회 | 중도 해지, 저축 목표 관리(예산 관리의 목표로 대체) |

### ⚪ 빼거나 자리만

| 기능 | 처리 | 이유 |
|---|---|---|
| 대출 중 서류·연체·중도상환 등 7개 | 뺌 | 외부 서류나 복잡한 계산이 필요하고 예산 관리와 연결이 약함. 넣는 9개는 🟡 표 참고 |
| 영업점 우대 (지점장 승인 금리) | `account_terms.rate_detail` JSON의 키(`source: BRANCH`, `approved_by`)로 **자리만** | 직원 역할·관리자 화면이 필요. 핵심 범위를 끝낸 뒤 "사람 승인" 흐름으로 만들 후보 |
| SNS·휴대폰·간편 인증 | 뺌 | 외부 연동 비용이 크고 핵심과 무관 |
| 자동이체 일반 기능 | 예산 관리의 **주기 끝 목표 저축 이체**만 | |

## 구현 순서

의존하는 것부터 만듭니다: `users → products → accounts → transfers → cards → loans → budget → agent`

| 순서 | 작업 | 이유 |
|---|---|---|
| 0 | CI (PR마다 테스트) | 이후 모든 PR을 자동 검사 |
| 1 | 핵심 테이블 교체 ([ADR 0003](../decisions/0003-db-redesign.md): 계좌·장부·승인 대기, users에 로그인·PIN 잠금 컬럼) + 로그인 잠금 | 이후 모든 기능이 이 구조 위에 만들어짐 |
| 2 | 보안 보강 (refresh token, 감사 기록) + 상품 (가입 조건, 우대금리, 특판, seed, 조회 API) | 인증은 모든 API가, 상품은 계좌·카드가 먼저 필요로 함 |
| 3 | 계좌 개설·조회 | |
| 4 | 이체 (잠금, 멱등키, 한도) | 돈 처리의 기준이 되는 로직. 카드·예산이 재사용 |
| 5 | 거래내역 + 카테고리 | 예산 분석의 재료 |
| 6 | 카드 결제 | |
| 7 | 대출 (가볍게) | 이체 로직 재사용. 상환액이 예산의 고정 지출이 됨 |
| 8 | 예산 관리 | 4~7을 모두 사용 |
| 9 | 자연어 Agent + RAG | 모든 기능의 API를 MCP 도구로 사용 |
| 10 | 화면 | |
| 11 | 배포 | |

화면(10)은 API가 생길 때마다 조금씩 붙여도 됩니다. 마감일이 정해지면 이 순서에서 범위를 줄입니다.

## 팀 기획과의 차이

| 팀 기획 | 이 레포 |
|---|---|
| 기능 41개 | 위 범위. 대출은 16개 중 9개, 예산 관리 추가 |
| 저축 목표 관리 (예·적금 10번) | 예산 관리의 목표 저축으로 통합 |
| 자동이체 (계좌 7번) | 예산 관리의 주기 끝 저축 이체만 |
